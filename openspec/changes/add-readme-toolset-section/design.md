## Context

См. `proposal.md` — Why. Существенные для подхода ограничения текущего состояния:

- `README.md` в состав поставки не входит (`PAYLOAD_PATHS` в `install.sh` перечисляет
  `docker-compose.yml`, `Makefile`, `.env.example`, `CLAUDE.md`, `AGENTS.md`, `rules`,
  `tools/host-runner`), а `rules/documentation-rules.md` — входит. Правка README остаётся
  внутренним делом репозитория, правка правил меняет содержимое поставки.
- Блок бейджей уже показывает шесть характеристик, включая версии Python, OpenSpec, uv, тег базового
  образа и версию набора. Способность `readme-badges` запрещает ручные копии этих значений в тексте
  `README.md`.
- [DOC-015](../../../rules/documentation-rules.md#ссылки-doc-015) требует относительных ссылок
  и допускает абсолютные URL только в блоке бейджей. Внешних ссылок в `README.md` сейчас нет вовсе.
- Базовый образ взят по плавающему тегу `latest` (`FROM ghcr.io/united-software-platform/claude:latest`),
  собственной закреплённой версии у него нет.
- `README.md` содержит незакоммиченные правки (`git status`), а `rules/` затрагивает параллельный
  change `revise-kit-composition` — по `reading-rules.md` и `terminology.md`, файла
  `documentation-rules.md` он не касается.

## Goals / Non-Goals

**Goals:**

- Один раздел, из которого виден весь состав набора: что это, откуда берётся, зачем нужно.
- Ссылка на источник каждого элемента прямо из перечня — на названии пункта.
- Исключение DOC-015 расширяется ровно на одно новое место и остаётся проверяемым по документу
  правил.

**Non-Goals:**

- Не меняются `Dockerfile`, пайплайны, установщик и состав образа: change документационный.
- Не переносится и не удаляется блок бейджей — перечень его не заменяет, а на него опирается.
- Не закрепляется версия базового образа: `latest` остаётся, замена его на закреплённый тег меняет
  политику обновления образа и требует правки способности `agent-image` — отдельный change.
- Не заводится проверка соответствия перечня `Dockerfile`: версий в перечне нет, сверять нечего.
- Не заводится извлечение фактических версий из сборки в GitHub Actions: пайплайн их знает, но
  доставка значений в `README.md` требует либо машинного коммита в `main` (запрещён
  [GIT-009](../../../rules/git-rules.md#формат-сообщения-коммита) и
  [GIT-010](../../../rules/git-rules.md#формат-сообщения-коммита), исключение есть только
  для релизного коммита), либо публикации значений на GitHub Pages. Обе цены выше выигрыша:
  Python и uv закреплены в `Dockerfile` и уже видны бейджами.

## Decisions

### Размещение — отдельный раздел «Состав набора» после навигации

Раздел ставится первым содержательным разделом, до «Установки». Альтернативы:

- Внутри «Образ окружения агента» — отвергнуто: раздел лежит за «Установкой» и «Что попадает
  в проект», а состав нужен до решения об установке; кроме того, перечень шире образа.
- Прямо после назначения, до навигации — отвергнуто:
  [DOC-014](../../../rules/documentation-rules.md#структура-файла) требует порядка «заголовок →
  назначение → навигация», и вставка раздела между ними его нарушает.

### Форма — маркированный список из двух групп

Перечень оформляется списком, а не таблицей: пункты неоднородны — у части элементов есть внешний
источник, у части нет, — и таблица дала бы колонку с пустыми ячейками, а описания сжала бы до
телеграфного стиля ради ширины колонок. Список читается сверху вниз и вмещает формулировку
«зачем и как используется», ради которой раздел и делается.

Две группы с вводными фразами заменяют признак происхождения у каждого пункта:

| Группа | Пункты | Ссылка названия |
|--------|--------|-----------------|
| Инструменты образа | `claude` | `https://github.com/united-software-platform/claude` |
| | OpenSpec | `https://github.com/Fission-AI/OpenSpec` |
| | Python | `https://www.python.org` |
| | uv | `https://github.com/astral-sh/uv` |
| Появляется в проекте | Окружение агента | без ссылки: файлы перечислены в описании |
| | Правила репозитория | `./rules` |
| | host-runner | `./tools/host-runner` |
| | Skills и команды SDD | без ссылки: источник — утилита OpenSpec, уже названная выше |

Альтернатива с таблицей из трёх колонок рассмотрена и отвергнута: колонка источника у половины
пунктов пустует, а третья колонка вынуждает сокращать описание. Альтернатива с двумя отдельными
разделами (образ и проект) отвергнута: она воспроизводит разбросанность, ради устранения которой
раздел вводится.

Собственные проверки репозитория (`tools/make-lint/`) в перечень не попадают — они не входят ни
в образ, ни в поставку; граница проговаривается в тексте раздела и отсылает к разделу «Разработка
самого kit'а».

### Описание отвечает «зачем и как», формулировка источника берётся, когда она это делает

| Элемент | Описание | Происхождение формулировки |
|---------|----------|----------------------------|
| `claude` | Образ окружения: агент Claude Code работает в контейнере, видит только каталог проекта и ходит в git под отдельным аккаунтом и ключом | описание репозитория, сжатое |
| OpenSpec | Ведёт SDD-процесс: командами `/opsx:*` создаёт change-артефакты и спецификации в `openspec/` | описание репозитория плюс способ применения |
| Python | Расширяет возможности агента | роль в наборе: формулировка python.org описывает язык вообще |
| uv | Менеджер зависимостей для Python | роль в наборе: формулировка репозитория говорит о скорости и Rust |
| Окружение агента | `docker-compose.yml`, `Makefile`, `.env.example` — контейнер поднимается и обслуживается целями `make` | порядок установки |
| Правила репозитория | `rules/`, `CLAUDE.md`, `AGENTS.md` — агент читает их перед задачей | состав `rules/` |
| host-runner | Позволяет агенту запускать команды `make` на вашей машине — например, поднять или перезапустить контейнер; без него агент видит только исходники. Ставится по желанию | `tools/host-runner/README.md`, раздел «Зачем это нужно» |
| Skills и команды SDD | `.claude/skills/`, `.claude/commands/`, `openspec/` — рабочие процессы `/opsx:*`, разворачивает `make init` | порядок установки |

Формулировки источников переводятся на русский по
[DOC-001](../../../rules/documentation-rules.md#язык-и-терминология), названия инструментов
и термины без устоявшегося перевода остаются как есть по DOC-003.

Внутренние понятия набора в описания не выносятся. Читатель перечня ещё не открывал ни профильный
раздел, ни документацию компонента, поэтому «белый список целей», «узкий канал», «мультиарх-образ»
для него пусты: описание говорит, что элемент позволяет сделать, а устройство остаётся по ссылке.

Альтернатива — везде цитировать источник — отвергнута: для Python и uv цитата описывает инструмент
вообще и не объясняет, почему он в наборе. Обратная альтернатива — везде свои описания — отвергнута
тоже: там, где источник роль объясняет, собственная формулировка расходилась бы с тем, что читатель
увидит по ссылке. Ограничение: описание не приписывает инструменту свойств, которых источник
не называет.

### Версии в перечень не выносятся

Номеров версий в перечне нет: версии показывает блок бейджей, а раздел на него ссылается.
Рассмотренные альтернативы:

- Бейджи в пунктах перечня — отвергнуто: та же информация появляется в документе дважды,
  а исключение DOC-015 пришлось бы расширять ещё и на изображения бейджей вне блока.
- Номера версий текстом — отвергнуто: ручная копия расходится с источником незаметно, и особенно
  быстро у OpenSpec, чья точная версия разрешается пайплайном при каждой сборке в пределах мажорного
  разряда.

Цена решения: версия и назначение инструмента разнесены по документу — читатель видит их не в одной
строке. Компенсируется отсылкой из раздела к блоку бейджей и к файлам-источникам `Dockerfile`
и `VERSION`, которые остаются читаемыми и без бейджей.

### Пункт образа называется `claude`

Бейдж шапки показывает `ghcr.io/united-software-platform/claude` вместе с тегом — это образ
организации, а не продукт Claude Code, у которого своя нумерация. Пункт называется именем образа —
`claude`, — а не ролью «базовый образ»: роль описывает место образа в сборке kit'а и в перечне
состава ничего не добавляет, тогда как имя совпадает с бейджем и с `FROM` в `Dockerfile`.

Тег базового образа при этом остаётся плавающим (`latest`) — раздел это отражает, не выдавая тег
за закреплённую версию.

### Правка DOC-015 — перечисление двух мест вместо одного

В `rules/documentation-rules.md` формулировка «действует только в блоке бейджей `README.md`»
заменяется перечнем из двух мест: блок бейджей между заголовком и назначением и названия пунктов
перечня состава — там, где цель ссылки внешняя. Остальные границы исключения — запрет HTML
по DOC-005 и требование относительной ссылки на файл внутри репозитория — сохраняются дословно.

Альтернатива «разрешить абсолютные ссылки в `README.md` где угодно» отвергнута: исключение перестало
бы быть проверяемым, а абсолютные URL расползлись бы по документу, для которого DOC-015 и написан.

### Разгрузка существующих разделов — ссылка вместо перечня

Строка «Состав» в таблице образа, вводные фразы разделов «Что попадает в проект» и «Опционально:
host-runner» заменяются ссылкой на новый раздел. Таблицы расположений в «Что попадает в проект»
остаются: они отвечают на другой вопрос — куда установщик пишет файлы, — и перечнем инструментов
не являются.

## Risks / Trade-offs

- **Версия и назначение разнесены по документу** → раздел прямо указывает, где смотреть версии;
  блок бейджей виден на первом экране, до самого раздела. Точная разрешённая версия OpenSpec
  в `README.md` по-прежнему не видна: бейдж показывает закреплённое в `Dockerfile` значение,
  а фактическую версию сборки — только лог пайплайна.
- **Внешние ссылки протухают** → их четыре, и все ведут на репозитории и сайты проектов, а не
  на страницы версий; проверяются при правке раздела, автоматической проверки ссылок в репозитории
  нет.
- **Описание расходится с источником** → источник может переписать формулировку у себя; сверка
  выполняется при правке раздела, автоматической сверки нет. Для строк с прямой формулировкой роли
  расхождение безвредно: они и не воспроизводят источник.
- **Расширение DOC-015 уходит в чужие проекты** → расширение снимает запрет, а не вводит новый:
  существующие документы установленных проектов остаются валидными. Правка `rules/` меняет
  содержимое поставки, поэтому требует повышения версии набора релизным сценарием.
- **Новый раздел — ещё одно место, которое можно забыть обновить** → требование единственности
  перечня в `readme-toolset` делает его единственным местом: остальные разделы ссылаются на него,
  и забыть остаётся ровно одно место вместо четырёх.
- **Плавающий тег базового образа остаётся** → перечень версий не приводит вовсе, поэтому `latest`
  за закреплённую версию не выдаётся; закрепление выносится в отдельный change по способности
  `agent-image`.

## Migration Plan

Отдельной миграции нет: изменение затрагивает документы. Порядок — правило, затем README, чтобы
на каждом шаге документ соответствовал действующей норме:

1. Расширить исключение DOC-015 в `rules/documentation-rules.md` и дописать строку в его таблицу
   версий.
2. Добавить раздел состава и пункт навигации в `README.md`, разгрузить три существующих раздела,
   дописать строку в таблицу версий `README.md`.
3. Откат — обратные правки тех же двух файлов; внешних систем изменение не касается.

Незакоммиченные правки `README.md` фиксируются отдельным коммитом до начала работы —
[GIT-020](../../../rules/git-rules.md#гейт-редактирования).

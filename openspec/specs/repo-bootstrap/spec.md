# repo-bootstrap Specification

## Purpose
Описывает наблюдаемый порядок и предусловия сборки рабочего контейнера Claude Code + OpenSpec,
одинаковый для разработчика и CI, до момента готовности контейнера к рабочей сессии агента.

Границы способности: подготовка проекта к запуску — установка поставки, генерация SSH-ключа
и конфигурации SSH — описана способностью `kit-installation`; устройство канала к целям `make`
на хосте — способностью `host-runner`. Здесь фиксируется только рантайм контейнера: что должно
быть готово до старта и что контейнер видит после него.

## Requirements

### Requirement: Предусловия запуска через файл окружения
Сборка и запуск контейнера SHALL требовать наличие файла `.env` с обязательными переменными
окружения. Без файла `.env` или без обязательных переменных запуск контейнера MUST завершаться
ошибкой конфигурации, а не запуском с неполным окружением.

#### Scenario: Запуск без .env
- **WHEN** каталог репозитория не содержит `.env`
- **THEN** запуск контейнера завершается ошибкой конфигурации до начала работы агента

#### Scenario: Запуск с заполненным .env
- **WHEN** `.env` содержит все обязательные переменные окружения
- **THEN** контейнер собирается и запускается без дополнительного вмешательства пользователя

### Requirement: Изоляция профиля аккаунта
Контейнер SHALL видеть только каталог аккаунта, соответствующий заданному профилю (`CLAUDE_PROFILE`).
Контейнер MUST NOT получать доступ на чтение к каталогам других профилей аккаунтов, размещённых
рядом в каталоге всех аккаунтов.

#### Scenario: Профиль не задан
- **WHEN** переменная `CLAUDE_PROFILE` не задана при запуске
- **THEN** контейнер монтирует несуществующий каталог профиля и не получает доступ к каталогам
  существующих профилей

#### Scenario: Профиль задан
- **WHEN** переменная `CLAUDE_PROFILE` указывает на существующий каталог аккаунта
- **THEN** контейнер видит только этот каталог как каталог конфигурации Claude Code

### Requirement: SSH-ключи приходят монтированием, а не из образа
Контейнер SHALL получать SSH-ключи для работы с удалённым git-репозиторием исключительно через
смонтированный каталог ключей хоста. Образ MUST NOT содержать приватных ключей: ключ принадлежит
разработчику и его окружению, а не поставке, поэтому ни сборка образа, ни его публикация не должны
ни создавать ключи, ни переносить их между окружениями.

Требование ужесточается публикацией образа: образ окружения агента публикуется в реестр контейнеров
и доступен для загрузки анонимно, поэтому приватный ключ, попавший в слой образа, стал бы публично
доступным.

Подготовка самих ключей — генерация пары, конфигурация SSH, права доступа — описана способностью
`kit-installation` и в объём этого требования не входит: здесь фиксируется только способ, которым
ключи попадают в контейнер.

#### Scenario: Push из контейнера
- **WHEN** каталог ключей хоста смонтирован в контейнер, а ключ зарегистрирован в git-сервисе
- **THEN** команды git внутри контейнера аутентифицируются этим ключом без дополнительной настройки

#### Scenario: Образ собран заново
- **WHEN** образ пересобран с нуля
- **THEN** приватных ключей в нём нет, а доступ к git появляется только после монтирования каталога
  ключей хоста

#### Scenario: Образ получен из реестра
- **WHEN** контейнер запущен на образе, загруженном из реестра контейнеров
- **THEN** приватных ключей в образе нет, а доступ к git появляется только после монтирования
  каталога ключей хоста

### Requirement: Единый порядок бутстрапа для разработчика и CI
Последовательность действий по подготовке окружения (получение образа окружения агента, запуск
сессии агента с профилем аккаунта, готовность к работе) SHALL быть одной и той же независимо
от того, кто её выполняет — разработчик вручную или CI-система. Различаться MAY только среда
выполнения команд запуска, а не сам порядок шагов.

Образ SHALL приходить из реестра контейнеров в обоих случаях. Локальная сборка образа MUST NOT
входить в порядок бутстрапа: она давала бы разработчику и CI-системе образы разного происхождения,
и совпадение результата перестало бы быть гарантированным.

Обновление образа до актуального SHALL быть отдельной командой, а не побочным действием запуска
сессии: запуск сессии MUST оставаться выполнимым без сетевого доступа, если образ нужного тега уже
загружен.

#### Scenario: Бутстрап в CI
- **WHEN** CI выполняет тот же порядок шагов получения образа и запуска, что и разработчик вручную
- **THEN** результат — готовая рабочая сессия агента — не отличается от сессии, запущенной
  разработчиком

#### Scenario: Происхождение образа
- **WHEN** разработчик и CI-система выполнили бутстрап при одном и том же закреплённом теге образа
- **THEN** оба получили образ из реестра контейнеров, а не собрали его локально

#### Scenario: Запуск сессии без сети
- **WHEN** пользователь запускает агента при недоступной сети и уже загруженном образе нужного тега
- **THEN** сессия открывается на загруженном образе, а попытка обновления образа не выполняется

### Requirement: Бутстрап не зависит от доступа к Docker-сокету
Контейнер агента MUST NOT получать доступ к Docker-сокету хоста: сокет дал бы контейнеру полный
контроль над хостом, что несоразмерно задаче работы с исходным кодом.

Отсутствие такого доступа MUST NOT блокировать бутстрап: контейнер получает образ, запускается
и остаётся пригодным для работы с исходным кодом независимо от того, может ли агент выполнять
цели `make` на хосте. Канал к целям `make` опционален, а его устройство — белый список целей,
токен, режим выполнения — описано способностью `host-runner` и в объём этого требования не входит.

#### Scenario: Канал к целям make недоступен
- **WHEN** раннер целей `make` на хосте не запущен
- **THEN** контейнер по-прежнему получает образ и запускается, а вызовы целей `make` из контейнера
  завершаются ошибкой соединения, не влияя на остальную работу агента

#### Scenario: Штатный запуск контейнера
- **WHEN** контейнер агента запущен по штатной конфигурации окружения
- **THEN** внутри контейнера нет доступа к Docker-сокету хоста

### Requirement: Рабочая сессия агента открывается эфемерным контейнером
Рабочая сессия агента SHALL начинаться запуском контейнера, живущего ровно столько, сколько длится
сессия: контейнер создаётся на время работы и удаляется по её завершении. Фоновый контейнер агента,
переживающий сессию, MUST NOT требоваться ни для одной операции окружения.

Профиль аккаунта SHALL задаваться переменной окружения на запуске сессии — значением из файла
окружения или переопределением в команде запуска. Отдельная операция входа в оболочку контейнера
MUST NOT требоваться для работы с агентом.

Запуск сессии MUST NOT зависеть от предварительного запуска контейнера другой операцией: одна
команда SHALL приводить пользователя из подготовленного проекта в работающую сессию агента.

#### Scenario: Начало рабочей сессии
- **WHEN** пользователь запускает агента в подготовленном проекте
- **THEN** контейнер создаётся, агент работает в текущем терминале, и предварительного запуска
  контейнера отдельной операцией не потребовалось

#### Scenario: Завершение рабочей сессии
- **WHEN** пользователь завершает работу агента
- **THEN** контейнер сессии удаляется, и отдельной операции остановки контейнера не требуется

#### Scenario: Запуск с профилем, отличным от файла окружения
- **WHEN** пользователь указывает профиль аккаунта переменной окружения в команде запуска
- **THEN** сессия открывается с этим профилем, а файл окружения проекта не редактируется

### Requirement: Команда контейнера по умолчанию запускает агента
Конфигурация окружения SHALL задавать сервису агента команду по умолчанию, запускающую Claude Code.
Запуск сессии без явной команды MUST приводить к работающему агенту, а не к завершению контейнера
на неизвестной команде.

Аргумент, переданный после имени сервиса, SHALL заменять команду по умолчанию: так выполняются
разовые операции в окружении контейнера — оболочка, git, инициализация инструментов SDD.

#### Scenario: Штатный запуск окружения
- **WHEN** пользователь открывает сессию агента при заполненном `.env`, не передавая команду
- **THEN** в контейнере работает агент, и дополнительных действий для входа в него не требуется

#### Scenario: Команда по умолчанию не существует в образе
- **WHEN** конфигурация окружения задаёт сервису команду, которой в образе нет
- **THEN** контейнер завершается сразу после запуска, и это дефект конфигурации поставки,
  а не ошибка пользователя

#### Scenario: Разовая операция вместо агента
- **WHEN** контейнер запускается с явно переданной командой после имени сервиса
- **THEN** выполняется переданная команда, а команда по умолчанию не запускается

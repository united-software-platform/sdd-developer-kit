## Why

Состав образа окружения агента обновляется вне репозитория: базовый образ Claude Code выходит
по нескольку раз в день, утилита OpenSpec разрешается из npm-реестра в момент сборки. Пользователь
набора ждёт от окружения свежести — это его продукт, — но kit доставляет свежий состав по суточному
расписанию, проверяет его формально и не сообщает, что внутри.

Три следствия наблюдаемы прямо сейчас:

- **Доставка отстаёт на случайную величину.** Единственный триггер, ловящий внешние обновления, —
  расписание раз в сутки. Между прогонами выходит несколько выпусков Claude Code, и пользователь
  не получает их никогда: образ собирается на том выпуске, что оказался свежим в момент прогона.
- **Проверка не смотрит на существо.** Перед публикацией сверяются номера версий и запуск
  инструментов. Утилита OpenSpec при этом разрешается в пределах мажорного разряда, а её данные —
  `openspec/specs/` и `openspec/changes/` — лежат в проекте пользователя и созданы прошлой версией.
  Минорный выпуск, перестающий понимать эти артефакты, проходит проверку и уезжает ко всем.
- **Состав образа не наблюдаем.** Версии, разрешаемые при сборке, не записываются ни в метки образа,
  ни в носитель, читаемый бейджами `README.md`. Бейдж базового образа показывает `latest` — истинного
  выпуска не называет; бейдж OpenSpec берёт значение из `ARG OPENSPEC_VERSION` и показывает `1.11.0`,
  тогда как в опубликованном образе `1.13.0`. Метки `title`, `description` и `url` унаследованы
  от базового образа, и опубликованный образ представляется в реестре как `claude`.

Цена приоритета свежести — отсутствие аварийного выхода: тег версии перезаписывается каждой
пересборкой, а digest, названный в `agent-image` единственным способом закрепить неизменность,
в поставляемую конфигурацию окружения не вписывается — шаблон имени образа жёстко вставляет
двоеточие перед тегом.

## What Changes

- Пересборка образа запускается событием публикации базового образа, а не ожиданием расписания.
  Расписание сохраняется как страховка на случай, если наверху обновлений нет. Утилита OpenSpec
  приезжает попутно: её версия разрешается заново на каждом прогоне независимо от причины запуска.
- Пересборка не выполняется, когда состав не изменился: разрешённые версии компонентов сверяются
  с составом уже опубликованного образа.
- Проверка перед публикацией подтверждает, что утилита OpenSpec понимает артефакты OpenSpec —
  на корпусе спецификаций и изменений самого репозитория kit'а, а не только сообщает свою версию.
- Разрешённые версии компонентов записываются в метки опубликованного образа; метки, описывающие
  сам образ, перестают наследоваться от базового.
- Бейджи `README.md` для компонентов, версия которых разрешается при сборке, берут значение
  из носителя, который пишет пайплайн, а не из `Dockerfile`.
- Каждый опубликованный состав получает тег, который не перезаписывается последующими пересборками.
  Конфигурация окружения в составе поставки допускает адресацию образа по digest.

Закрепление версий Python и uv не меняется: их обновление остаётся осознанной правкой исходника
образа. Разряд версии kit'а по-прежнему выбирает человек при запуске релизного сценария —
автоматическая инкрементация по изменению состава не вводится: на движущемся теге её никто не читает,
а номер kit'а сохраняет смысл «состояние исходников».

## Capabilities

### New Capabilities

Новых способностей нет: изменение уточняет поведение трёх существующих.

### Modified Capabilities

- `agent-image`: события пересборки (запуск по публикации базового образа, отказ от пересборки
  при неизменном составе), состав проверки перед публикацией (совместимость утилиты OpenSpec
  с артефактами), состав метаданных опубликованного образа (версии разрешаемых компонентов,
  собственные описательные метки), схема тегов (неперезаписываемый тег состава).
- `readme-badges`: источник значений бейджей для компонентов, версия которых разрешается
  при сборке, а не записана в `Dockerfile`.

Требование о форме ссылки на образ в поставляемой конфигурации окружения принадлежит `agent-image`
(«Установленный проект использует опубликованный образ»), поэтому `kit-installation` изменения
не требует: состав и структура установки не меняются.

## Impact

- Пайплайн сборки образа: `.github/workflows/docker-agent.yml` — триггер, сверка состава,
  проверка совместимости, метки, схема тегов.
- Пайплайн репозитория базового образа `united-software-platform/claude` — отправка события
  о публикации. Это единственная правка вне этого репозитория; связь между репозиториями
  появляется впервые.
- `README.md` — источник значений двух бейджей; `Dockerfile` — роль `ARG OPENSPEC_VERSION`
  как значения по умолчанию для локальной сборки, а не источника бейджа.
- Состав поставки: `docker-compose.yml` — форма ссылки на образ. Перечень путей поставки
  не меняется, но изменённый файл доезжает до установленных проектов при следующей установке.
- Носитель разрешённых версий появляется в репозитории впервые; его согласование с `VERSION`
  и с границами автоматизации git-операций разбирается в design.

## Context

Мотивация — в [proposal.md](./proposal.md), требования — в [specs/repo-versioning/spec.md](./specs/repo-versioning/spec.md).
Подход определяют четыре свойства текущего состояния репозитория.

Установщик читает версию из файла, а не из git: архив, который он загружает с GitHub, приходит без
истории (`install.sh:146-150`, комментарий там же). Любой механизм, оставляющий версию только в теге,
лишает установщик источника значения.

`Makefile` входит в состав поставки, а файл `VERSION` — нет. Всё, что попадает в `Makefile`, уезжает
в каждый установленный проект, где файла версии не существует. Сам перечень путей поставки живёт
в `install.sh` переменной `PAYLOAD_PATHS`, то есть в исполняемом коде, а не в данных.

Формат сообщения коммита зафиксирован как `{CODE}-NNN: описание`
([GIT-009](../../../rules/git-rules.md#формат-сообщения-коммита)) и не несёт признака major/minor/patch,
поэтому инструменты, выводящие разряд из Conventional Commits, к репозиторию неприменимы без слома
действующего правила.

CI в репозитории нет ни в каком виде: `.github/workflows` отсутствует. Пайплайн вводится этим change
с нуля.

## Goals / Non-Goals

**Goals:**

- Один источник истины о версии, читаемый без git-истории.
- Релиз одним действием человека, без обрядов вокруг него.
- Обнаружение пропущенной инкрементации без участия человека.
- Отсутствие следов механизма в установленных проектах.

**Non-Goals:**

- Публикация GitHub Release и артефактов релиза.
- Автоматический выбор разряда и любая привязка инкрементации к шагам процесса OpenSpec.
- Версионирование установленных проектов и перенос механизма в поставку.
- Замена формата коммитов на Conventional Commits.

## Decisions

### Файл версии — истина, тег — метка

`VERSION` хранит номер без префикса и остаётся единственным носителем, доступным установщику.
Аннотированный тег `vX.Y.Z` добавляется поверх и служит адресом для ключа `--ref`.

Альтернатива «только тег» отвергнута: она ломает `install.sh:148`, где отсутствие файла — фатальная
ошибка, и лишает манифест поля `kit_version`. Альтернатива «только файл» отвергнута: без тега ключ
`--ref` остаётся без единого воспроизводимого значения, а значит невоспроизводима и установка.

Префикс `v` добавляется на стороне предъявления — в имени тега и в шаблоне бейджа. Запись `v1.0.0`
прямо в файл потребовала бы правки разбора в `install.sh:149` и изменила бы значение `kit_version`
в манифестах, уже созданных у пользователей.

### Релиз — вручную запускаемый workflow, локального инструмента инкрементации нет

Релиз выполняет `.github/workflows/release.yml`, запускаемый через `workflow_dispatch` с двумя
параметрами: разряд (`major`/`minor`/`patch`) и код задачи. Он читает `VERSION`, повышает разряд,
коммитит, ставит аннотированный тег `vX.Y.Z` и публикует его. Локального скрипта инкрементации
в репозитории нет.

Альтернатива «локальный `bump.sh` + ручные коммит и тег» рассматривалась и отвергнута по цене: скрипт
занимал 145 строк, из которых собственно инкрементация — четыре, а остальное разбор ключей, гейт
незакоммиченных правок и печать четырёх git-команд, которые человек всё равно копирует руками. Прибавить
единицу к номеру в файле из одной строки — не та задача, ради которой держат инструмент; при этом
разойтись руками с тем, что делает CI, такой скрипт вполне мог.

Альтернатива «цель `make version-bump`» отвергнута по составу поставки: `Makefile` копируется в целевые
проекты, и цель падала бы там на отсутствующем `VERSION`, нарушая обещание `README.md` о том, что в
установленном проекте работает весь список `make help`.

Побочный выигрыш решения — согласованность носителей по построению: файл, коммит и тег появляются
одним запуском, поэтому состояние «тег указывает на коммит с другим номером» не возникает и сторожить
его отдельной проверкой не нужно.

Цена: релиз перестаёт быть локальной командой и выполняется в интерфейсе GitHub, а релизному workflow
нужно право `contents: write`.

### Код задачи — параметр запуска

Сообщение релизного коммита обязано соответствовать `{CODE}-NNN: описание`
([GIT-009](../../../rules/git-rules.md#формат-сообщения-коммита)), а выводить номер задачи из контекста
запрещает [GIT-010](../../../rules/git-rules.md#формат-сообщения-коммита). Workflow не может ни выдумать
номер, ни спросить его после запуска, поэтому код задачи задаётся вторым входным параметром и
подставляется в заголовок: `SDDT-012: релиз v1.1.0`.

Альтернатива «освободить релизный коммит от GIT-009» отвергнута: правило не знает исключений по автору
коммита, а исключение ради одного сценария обесценило бы машинную проверку заголовков.

### Разряд задаёт человек, а не разметка артефактов

Разряд задаётся входным параметром запуска — `major`, `minor` или `patch`. Автоматический вывод
разряда не вводится.

Такой вывод рассматривался: разметка delta-спек (`ADDED`/`MODIFIED`/`REMOVED Requirement`) —
единственный машиночитаемый признак характера изменения в этом репозитории, и по ней несложно
отобразить `REMOVED` → major, `ADDED` → minor, иначе patch. Отвергнут по двум причинам.

Во-первых, разметка не различает несовместимые изменения внутри `MODIFIED Requirement`: вывод занижал
бы разряд именно там, где ошибка дороже всего, — при поломке совместимости. Автоматика, требующая
перепроверки в каждом случае, не экономит внимание, а тратит его.

Во-вторых, чтобы вывод срабатывал сам, его пришлось бы вызывать из сценария архивации change. Файлы
сценариев (`.claude/skills`, `.claude/commands`) входят в состав поставки и копируются в целевые
проекты, где нет ни `VERSION`, ни релизного workflow. Инструкция приехала бы туда невыполнимой.

Альтернатива «Conventional Commits + `release-please`» отвергнута отдельно: она требует смены формата
коммитов, зафиксированного GIT-009.

От пропуска инкрементации страхует не автоматический выбор разряда, а проверка в CI — см. следующее
решение.

### Два workflow: проверка и релиз

`version-check.yml` запускается на `pull_request` и на `push` в `main` и выполняет одну проверку:
изменение путей поставки при неизменном `VERSION`. База сравнения различается по событию: для
`pull_request` — точка ветвления от целевой ветки, для `push` — предыдущее состояние ветки.

`release.yml` запускается только вручную и ничего не проверяет. Разделение по событию запуска, а не
по смыслу: проверка обязана идти на каждое изменение, релиз — никогда сам по себе.

Проверка вынесена в `tools/version/check.sh`, а workflow остаётся тонкой обёрткой: тот же вердикт
доступен локально до отправки изменений.

### Список путей поставки — отдельный файл, а не переменная

`PAYLOAD_PATHS` переносится из `install.sh` в `payload.txt`: установщик читает файл построчно, проверка
читает тот же файл. Прежний вариант — вычитывать значение шелл-переменной из `install.sh` разбором
текста — работал, но проверка зависела от формы записи в чужом скрипте: перенос строки или смена кавычек
ломали разбор молча.

`payload.txt` лежит в корне репозитория и попадает в загружаемый архив, но сам в список путей поставки
не входит, поэтому в целевой проект не копируется.

## Risks / Trade-offs

- **CI обнаруживает пропуск только после отправки изменений** → это принятая цена простоты: другого
  средства, не позволяющего забыть инкрементацию, в репозитории нет, и это зафиксировано в спеке.
  `tools/version/check.sh` доступен локально до отправки. Git-хук не рассматривался: он не
  версионируется вместе с репозиторием и не переживает переустановку kit'а.
- **Разряд выбирает человек и может ошибиться** → цена ошибки — неточный номер версии, а не поломка
  установки; автоматический вывод разряда ошибался бы тише и опаснее.
- **Список путей поставки может разойтись у установщика и проверки** → обе стороны читают один
  `payload.txt`; собственной копии перечня нет ни у одной.
- **Тег поставлен вручную мимо релизного workflow** → расхождение возможно только так, и отдельной
  проверкой оно не сторожится: единственный штатный способ создать тег — запуск релизного workflow,
  а ручная расстановка тегов остаётся вне процесса.
- **Релизному workflow нужно право `contents: write`, и коммит идёт от имени бота** → права ограничены
  одним сценарием, запускаемым только вручную; автор коммита виден в истории, а заголовок по GIT-009
  несёт код задачи, введённый человеком при запуске.
- **Бейдж зависит от `shields.io` и от публичной доступности репозитория** → ограничение уже
  зафиксировано для блока бейджей в целом и не расширяется этим change.
- **Первые пайплайны в репозитории — новая зона отказа** → проверочный workflow ограничен одной
  проверкой без сборки образа и без секретов; его отказ не блокирует ни установку kit'а, ни локальную
  работу. Отказ релизного workflow не оставляет полусостояния: `VERSION`, коммит и тег появляются
  одним запуском, и неудачный прогон просто не публикует ничего.

## Migration Plan

1. Исходный тег `v1.0.0` ставится вручную один раз — значение уже лежит в `VERSION`, а релизного
   workflow на момент первой пометки ещё нет. Ретроспективная расстановка тегов для прошлых коммитов
   не выполняется: воспроизводимых релизов до этого change не было.
2. Проверка и оба workflow добавляются в том же change; все последующие релизы выполняются запуском
   релизного workflow, а не руками.
3. Откат: удаление `tools/version/`, обоих файлов workflow, возврат `PAYLOAD_PATHS` в `install.sh`
   и шаблона бейджа. Файл `VERSION` и выставленные теги при откате сохраняются — они уже могли попасть
   в манифесты установок.

## Open Questions

- Публикация GitHub Release при появлении тега — отдельная задача. Она не меняет ни спеки, ни состав
  работ этого change: тег остаётся адресом установки независимо от того, оформлен ли он релизом.

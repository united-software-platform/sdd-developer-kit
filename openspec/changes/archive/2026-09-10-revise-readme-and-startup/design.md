## Context

Мотивация — в [`proposal.md`](./proposal.md), раздел «Why». Здесь фиксируется техническая сторона:
что именно теряется вместе с целями `up`, `down`, `shell`, чем это компенсируется и как изменение
сочетается с соседними правками тех же файлов — применённой `add-readme-toolset-section`
и незавершённой `revise-kit-composition`.

Действующее состояние, важное для решений:

- `docker-compose.yml` описывает сервис `claude` в профиле `claude` с командой по умолчанию `claude`
  и монтированием каталога профиля `${CLAUDE_ACCOUNTS_DIR}/${CLAUDE_PROFILE:-__no_profile__}`;
- цель `up` перед запуском выполняет `docker compose pull` и при недоступном реестре печатает
  предупреждение, не прерывая запуск;
- цель `shell` проверяет, что `CLAUDE_PROFILE` задан и каталог профиля существует, и лишь затем
  выполняет `docker compose exec claude bash`;
- `Makefile` входит в состав поставки (`PAYLOAD_PATHS` в `install.sh`), поэтому изменение перечня
  целей меняет сценарий уже установленных проектов;
- `tools/host-runner/runner.py` держит белый список `{"up", "down", "init", "openspec-init", "help"}`.

## Goals / Non-Goals

**Goals:**

- Один способ начать работу с агентом — тот же, что документирован в репозитории базового образа.
- `README.md`, читаемый пользователем набора от начала до конца без пропуска чужих разделов.
- Сохранение изоляции профилей аккаунтов после удаления проверки из цели `shell`.

**Non-Goals:**

- Замена удалённых целей новой обёрткой `make` (решение пользователя: обёртки не вводим).
- Пересмотр состава образа, схемы тегов, пайплайнов сборки и механизма релиза — меняется только
  место, где они описаны.
- Пересмотр раздела состава набора и блока бейджей: раздел создан применённым изменением
  `add-readme-toolset-section` и здесь только получает новую ссылку вместо удаляемого раздела.

## Decisions

### Решение 1. Запуск агента — `docker compose run --rm claude`, без обёртки `make`

Команда совпадает с документированной в репозитории базового образа
`united-software-platform/claude`: `CLAUDE_PROFILE=<профиль> docker compose run --rm claude`.
Сервис уже имеет командой по умолчанию `claude`, профиль передаётся переменной окружения — правок
`docker-compose.yml`, кроме комментариев, не требуется.

Альтернатива — цель `make claude` с проверкой профиля — отклонена пользователем: набор не заводит
собственного интерфейса поверх команды, которая уже описана источником. Плата — утверждение
«прямые вызовы `docker compose` не нужны ни на одном шаге» перестаёт быть верным и снимается
из `README.md` и из требования способности `kit-installation`; прямой вызов остаётся ровно один.

### Решение 2. Изоляция профиля держится умолчанием compose, а не проверкой цели

Проверка «профиль задан и каталог существует» жила в рецепте `shell` и вместе с ним исчезает.
Защита от доступа к чужим профилям остаётся там же, где была изначально: подстановка
`${CLAUDE_PROFILE:-__no_profile__}` монтирует несуществующий каталог, а анонимный том прячет
каталог всех аккаунтов внутри контейнера. Требование `repo-bootstrap` «Изоляция профиля аккаунта»
этим и сформулировано — оно не меняется.

Что теряется: диагностика. Раньше опечатка в имени профиля давала внятную ошибку цели, теперь
агент стартует с пустым каталогом конфигурации и просит авторизацию заново. Компенсация —
абзац об этом в разделе запуска агента `README.md`: пустая авторизация означает неверный
`CLAUDE_PROFILE`.

Альтернатива — перенести проверку в `init` — отклонена: `init` выполняется до того, как каталог
профиля создан, и проверка на этом шаге всегда падала бы.

### Решение 3. Обновление образа — отдельная команда, а не побочный эффект запуска

`docker compose run` тянет образ только при его отсутствии, поэтому автоматическое обновление,
которое делала цель `up`, исчезает. Возвращать его флагом `--pull always` в документированной
команде запуска нельзя: запуск перестал бы работать без сети даже при готовом образе — ровно то
поведение, которое цель `up` обходила предупреждением.

Поэтому обновление выносится в отдельную команду `docker compose pull claude`, названную в разделе
запуска агента рядом с плановой пересборкой образа: пользователь решает, когда забирать обновление.
Требование `repo-bootstrap` фиксирует это как норму, а не как упущение.

### Решение 4. `CONTRIBUTING.md` — один документ для всего материала контрибьютора

Материал из `README.md` («Разработка самого kit'а», «Версия репозитория», устройство пайплайна
сборки образа) переносится в единственный новый документ репозитория. Дробить его на несколько
файлов на текущем объёме незачем: разделов три, и все адресованы одному читателю.

Выбор имени `CONTRIBUTING.md` — не только соглашение: файл не входит в `PAYLOAD_PATHS`, поэтому
в целевой проект не попадает, и требование `readme-badges` «описание не в документах поставки»
продолжает выполняться.

Перенос выполняется по [DOC-023](../../../rules/documentation-rules.md#жизненный-цикл-документа):
ключевые факты сохраняются, в `README.md` остаётся ссылка. Документ оформляется по
[DOC-014](../../../rules/documentation-rules.md#структура-файла) и получает собственную таблицу
версий по [DOC-022](../../../rules/documentation-rules.md#жизненный-цикл-документа).

### Решение 5. `DOC-015` формулируется критерием, а не третьим пунктом перечня

Применённое изменение `add-readme-toolset-section` расширило исключение `DOC-015` с одного места
до двух: блок бейджей и названия пунктов перечня состава. Этому изменению нужен внешний адрес
в третьем месте — в тексте раздела запуска агента.

Третий пункт в перечне мест превратил бы правило в реестр, который придётся дополнять при каждом
новом разделе. Вместо этого формулировка сводится к критерию: в `README.md` абсолютный URL допускается
там, где цель ссылки действительно внешняя — проект инструмента, внешний сервис бейджей, репозиторий
базового образа, — а ссылка на файл внутри репозитория остаётся относительной. Действующие два места
остаются примерами критерия, а не его определением.

Альтернатива — оставить перечень и дописать третий пункт — отклонена: правило уже переписывалось
ради второго места, и следующий раздел с внешней ссылкой потребовал бы четвёртой правки.

### Решение 6. Порядок относительно соседних изменений

`add-readme-toolset-section` уже применено к рабочему дереву: `README.md` содержит раздел состава
набора, ссылающийся на «Разработку самого kit'а», а `DOC-015` — исключение из двух мест. Это
изменение опирается на его результат: правит ссылку раздела состава на `CONTRIBUTING.md`
и обобщает `DOC-015` (Решение 5).

`revise-kit-composition` не применено и правит `docker-compose.yml` (команда сервиса `claude`,
комментарий профиля, висячий код `READ-008`) и правила. Это изменение трогает в том же файле только
комментарий о проверке профиля «в цели `make claude-shell`». Пересечение — один блок комментариев,
конфликт разрешается вручную при применении второго по очереди; ни одно из изменений другого
не отменяет.

Рекомендуемый порядок — `revise-kit-composition` перед этим изменением: сначала чинится состав
поставки, затем из `README.md` уходят лишние разделы. Обратный порядок допустим и требует лишь
разрешения конфликта в комментариях `docker-compose.yml`.

### Решение 7. Разряд версии — `minor`

Из поставки исчезают три цели `Makefile`. Формально это несовместимое изменение состава поставки,
но фактической функциональности пользователь не теряет: в установленных проектах `make up`
и `make shell` контейнер не поднимали — `docker-compose.yml` поставки передавал сервису
несуществующую команду (дефект, который чинит изменение `revise-kit-composition`). Работавшая
часть поставки — `init`, `openspec-init`, `help` — не тронута.

Поэтому разряд `minor`, а не `major`: документированный путь пользователя изменился (появился
новый способ запуска агента и документ `CONTRIBUTING.md`), но работоспособной совместимости
изменение не ломает. Для `patch` изменение слишком велико. Решение принял пользователь.

Релиз выполняется отдельным запуском сценария `release` и в задачи этого изменения не входит.

### Решение 8. Исключение `DOC-022` вводится по типу документа, а не для одного файла

Таблица версий уходит из `README.md`, а вместе с ней — и из `tools/host-runner/README.md`: правило
формулируется как «ни один `README.md` репозитория таблицу версий не ведёт». Точечное исключение
для одного файла потребовало бы обоснования, почему соседний `README.md` живёт по другой норме,
а такого обоснования нет: оба документа адресованы пользователю, и оба существуют в git.

Прочие документы — `rules/`, `CONTRIBUTING.md` — таблицу версий сохраняют: их читатель ведёт сам
репозиторий, и для него история правок документа — рабочая информация, а не шум.

Что теряется: колонки `Задача`, `Агент` и `Модель`, которых в git нет. Для `README.md` эта потеря
принимается: источник изменения фиксируется сообщением коммита по
[GIT-009](../../../rules/git-rules.md#формат-сообщения-коммита), а связь с задачей — его заголовком.
Для документов правил, где трассируемость важнее, таблица остаётся.

Удаление таблицы из `tools/host-runner/README.md` меняет состав поставки, но разряд релиза уже
поднят до `major` Решением 7 — отдельного повышения не требуется.

## Risks / Trade-offs

- **Пользователь установленного проекта теряет привычные команды.** → Ограничение фиксируется
  в `README.md` в разделе повторной установки и обновления: после обновления kit'а запуск агента
  выполняется командой среды контейнеризации, целей управления контейнером больше нет.
- **Неверный `CLAUDE_PROFILE` больше не диагностируется явно.** → Признак и лечение описаны
  в разделе запуска агента (Решение 2).
- **Образ перестаёт обновляться сам.** → Команда обновления названа в `README.md`, требование
  зафиксировано в `repo-bootstrap` (Решение 3).
- **host-runner теряет управление контейнером.** → Потери функциональности нет: агент живёт внутри
  эфемерного контейнера сессии и перезапустить её изнутри не мог бы и раньше — цель `up` из белого
  списка пересоздавала бы контейнер, в котором агент работает. В белом списке остаются `init`,
  `openspec-init`, `help`.
- **Три изменения правят `README.md` одновременно.** → Порядок и точки пересечения зафиксированы
  в Решении 6; таблица версий `README.md` заполняется по факту применения каждого изменения.
- **История правок `README.md` остаётся только в git.** → Потеря колонок `Задача`, `Агент`
  и `Модель` принята осознанно (Решение 8); существующие записи таблицы не переносятся в другой
  документ — они описывают правки файла, а не решения о наборе.
- **Ссылка на внешний репозиторий может устареть.** → Риск принят: альтернатива — копия чужой
  инструкции, расходящаяся с источником молча, что хуже видимой битой ссылки.

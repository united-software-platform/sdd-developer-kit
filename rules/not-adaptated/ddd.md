# Domain Driven Design (DDD)

Правила проектирования на основе предметной области. Применяются при моделировании доменной логики, разработке сервисов и проектировании границ модулей.

## Таблица правил

| ID | Правило |
|----|---------|
| DDD-001 | Единый язык (Ubiquitous Language) — все термины в коде, документах и разговорах совпадают |
| DDD-002 | Запрет технических синонимов для доменных понятий внутри одного контекста |
| DDD-003 | Каждый Bounded Context имеет явную границу и единую согласованную модель внутри |
| DDD-004 | Одно доменное понятие может иметь разный смысл в разных контекстах — это нормально |
| DDD-005 | Взаимодействие между контекстами — только через явный контракт (ACL, события, API) |
| DDD-006 | Агрегат — единица транзакционной согласованности; инвариант соблюдается внутри агрегата |
| DDD-007 | Корень агрегата (Aggregate Root) — единственная точка входа; прямой доступ к внутренним объектам запрещён |
| DDD-008 | Ссылки между агрегатами — только по идентификатору, не по объекту |
| DDD-009 | Один агрегат изменяется в одной транзакции; изменение нескольких агрегатов — через Domain Events |
| DDD-010 | Сущность (Entity) — идентифицируется по id, не по значениям свойств |
| DDD-011 | Жизненный цикл сущности отслеживается через Repository |
| DDD-012 | Value Object — идентифицируется по совокупности значений, не имеет id |
| DDD-013 | Value Object — всегда иммутабельный; изменение создаёт новый объект |
| DDD-014 | Валидация инвариантов Value Object — в конструкторе или фабрике; невалидный объект не создаётся |
| DDD-015 | Domain Event — факт, произошедший в домене; неизменяем после создания |
| DDD-016 | Название Domain Event — прошедшее время: `OrderPlaced`, `PaymentConfirmed` |
| DDD-017 | Domain Event содержит только данные, необходимые подписчику; никакой логики |
| DDD-018 | Domain Service применяется только если операция не принадлежит ни одной сущности/VO |
| DDD-019 | Domain Service не хранит состояние (stateless) |
| DDD-020 | Repository — интерфейс в Domain, реализация в Infrastructure |
| DDD-021 | Repository работает с агрегатами целиком; загрузка частей агрегата запрещена |
| DDD-022 | Запрет бизнес-логики в Repository; только операции хранения и выборки |
| DDD-023 | Factory инкапсулирует сложную логику создания агрегатов и сущностей |
| DDD-024 | Объект не создаёт сам себя — только через Factory или конструктор с явными аргументами |
| DDD-025 | ACL (Anti-Corruption Layer) — обязателен при интеграции с внешней системой или чужим контекстом |
| DDD-026 | ACL переводит чужую модель в термины своего контекста; внешняя модель не проникает в домен |

## Единый язык [DDD-001..002]

**[DDD-001]** Ubiquitous Language — единый словарь, общий для команды и кода. Имена классов, методов и переменных в коде совпадают с терминами, которые используют аналитики, разработчики и заказчики.

**[DDD-002]** Внутри одного Bounded Context нельзя использовать технические синонимы для доменного понятия. Если в домене есть `Order`, то не допускается `Cart`, `Purchase`, `Basket` как синонимы.

```
// Запрещено — разные имена для одного понятия
class Order { ... }
class ShoppingCart { ... }  // синоним Order в том же контексте

// Правильно — имя совпадает с языком домена
class Order { ... }
```

## Ограниченный контекст [DDD-003..005]

**[DDD-003]** Bounded Context — явно очерченная область с единой согласованной моделью и словарём. Граница может быть выражена как отдельный модуль, namespace, пакет или физически отдельный сервис — форма определяется архитектурным решением проекта.

**[DDD-004]** Одно слово может означать разное в разных контекстах — это намеренно. `User` в контексте `Billing` — плательщик с реквизитами; `User` в контексте `Support` — источник заявок.

```
// Billing Context
class User {
    billingAddress: Address
    paymentMethod: PaymentMethod
}

// Support Context
class User {
    supportTier: enum(basic, premium)
    openTicketsCount: int
}
```

**[DDD-005]** Взаимодействие между контекстами осуществляется только через явный контракт: ACL, Domain Events или HTTP API. Прямое использование классов соседнего контекста запрещено.

## Агрегат [DDD-006..009]

**[DDD-006]** Агрегат — кластер объектов, которые изменяются вместе и образуют транзакционную границу. Инварианты домена обеспечиваются внутри агрегата.

**[DDD-007]** Aggregate Root — единственная точка входа в агрегат. Внешний код взаимодействует только с корнем.

```
// Запрещено — прямой доступ к внутреннему объекту
order.lineItems.add(new LineItem(...))

// Правильно — через корень агрегата
order.addItem(productId, quantity, price)
```

**[DDD-008]** Ссылки на другие агрегаты хранятся только по идентификатору, не по объекту. Это предотвращает случайную навигацию по графу объектов.

```
// Запрещено — ссылка на объект другого агрегата
class Order {
    customer: Customer  // чужой агрегат
}

// Правильно — только идентификатор
class Order {
    customerId: CustomerId
}
```

**[DDD-009]** В одной транзакции изменяется ровно один агрегат. Когда бизнес-операция затрагивает несколько агрегатов — первый агрегат публикует Domain Event, остальные реагируют асинхронно.

```
// Order.place() изменяет только Order
// Публикует OrderPlaced — Inventory реагирует отдельно

TRANSACTION:
  order.place()            // изменяет один агрегат
  publish(OrderPlaced)     // сигнал для других контекстов

// Запрещено в одной транзакции:
  order.place()
  inventory.reserveItems() // второй агрегат
```

## Сущность [DDD-010..011]

**[DDD-010]** Entity — объект с идентичностью. Два объекта с одинаковым `id` считаются одним и тем же, даже если все остальные поля различаются.

```
Entity User:
    id: UserId          // определяет идентичность
    name: string        // может меняться
    email: Email        // может меняться

user1 = User(id=42, name="Иван")
user2 = User(id=42, name="Алексей")
user1 == user2          // true — один и тот же пользователь
```

**[DDD-011]** Жизненный цикл Entity (создание, обновление, удаление) управляется через Repository. Entity не сохраняет себя сама.

## Value Object [DDD-012..014]

**[DDD-012]** Value Object — объект без идентичности. Равенство определяется по значениям всех полей. Применяется для понятий, у которых нет осмысленного id: деньги, координаты, диапазон дат.

```
VO Money:
    amount: int
    currency: string

Money(100, "RUB") == Money(100, "RUB")  // true
Money(100, "RUB") == Money(200, "RUB")  // false
```

**[DDD-013]** Value Object иммутабелен. Нельзя изменить поле — нужно создать новый объект.

```
// Запрещено
price.amount = 200

// Правильно
newPrice = Money(200, price.currency)
```

**[DDD-014]** Инварианты проверяются при создании — невалидный Value Object не может существовать.

```
VO Email:
    constructor(value: string):
        if not matches(value, EMAIL_REGEX):
            throw InvalidEmailException
        this.value = value
```

## Domain Event [DDD-015..017]

**[DDD-015]** Domain Event фиксирует факт, который произошёл в домене. Неизменяем после создания. Не команда, не запрос — свершившийся факт.

**[DDD-016]** Имя события — глагол в прошедшем времени, отражает факт домена: `OrderPlaced`, `PaymentFailed`, `DocumentIndexed`.

```
// Запрещено — настоящее время или императив
event PlaceOrder
event IndexingDocument

// Правильно — прошедшее время
event OrderPlaced
event DocumentIndexed
```

**[DDD-017]** Domain Event содержит только данные, нужные подписчику. Никакой бизнес-логики.

```
Event OrderPlaced:
    orderId: OrderId
    customerId: CustomerId
    totalAmount: Money
    placedAt: Timestamp
    // только данные, никаких методов с логикой
```

## Domain Service [DDD-018..019]

**[DDD-018]** Domain Service применяется для операций, которые не принадлежат ни одной конкретной сущности или Value Object. Если операция явно принадлежит Entity — метод должен быть на ней.

```
// Запрещено — операция принадлежит Entity Order
Service OrderService:
    cancelOrder(order: Order): void

// Правильно — метод на сущности
Entity Order:
    cancel(): void

// Правильно использовать Service — операция над двумя агрегатами
Service TransferService:
    transfer(from: Account, to: Account, amount: Money): void
```

**[DDD-019]** Domain Service stateless — не хранит состояние между вызовами. Все данные передаются как аргументы.

## Repository [DDD-020..022]

**[DDD-020]** Repository — абстракция коллекции агрегатов. Интерфейс объявляется в Domain, реализация — в Infrastructure (см. [clean-architecture.md](clean-architecture.md), CLAR-002).

**[DDD-021]** Repository загружает и сохраняет агрегат целиком. Загрузка «части» агрегата нарушает инкапсуляцию и транзакционную границу.

```
// Запрещено — частичная загрузка агрегата
repository.findLineItemsByOrderId(orderId)

// Правильно — агрегат целиком
repository.findById(orderId): Order
```

**[DDD-022]** Repository не содержит бизнес-логики — только операции хранения и выборки.

```
// Запрещено — бизнес-логика в репозитории
repository.cancelExpiredOrders()

// Правильно — репозиторий только читает/пишет
repository.findExpiredOrders(): List<Order>
// бизнес-логику применяет UseCase
```

## Factory [DDD-023..024]

**[DDD-023]** Factory инкапсулирует сложную логику создания агрегата или сущности: генерацию идентификатора, выбор начального состояния, применение правил создания.

```
// Запрещено — логика создания разбросана по UseCase
useCase.execute():
    id = generateUuid()
    status = "draft"
    if user.isPremium: limit = 100 else: limit = 10
    order = Order(id, status, limit, ...)

// Правильно — Factory инкапсулирует правила создания
Factory OrderFactory:
    create(customer: Customer, items: List<Item>): Order
        id = IdGenerator.next()
        limit = LimitPolicy.forCustomer(customer)
        return Order(id, status=DRAFT, limit, items)
```

**[DDD-024]** Объект не создаёт сам себя (`new self`, `new static`). Создание — через Factory или явный конструктор с внешними аргументами (см. [php-style.md](php-style.md), PHP-004, PHP-008).

## Anti-Corruption Layer [DDD-025..026]

**[DDD-025]** ACL обязателен при интеграции с внешней системой (legacy, сторонний API) или с другим Bounded Context. Защищает доменную модель от чужих концепций и терминов.

**[DDD-026]** ACL транслирует внешнюю модель в термины своего контекста. Внешние DTO, структуры или объекты не проникают вглубь домена.

```
// Внешняя система возвращает свою модель
ExternalUser:
    usr_id: string
    usr_email: string
    account_type: int   // 1=basic, 2=premium

// ACL переводит в модель нашего контекста
ACL UserACL:
    translate(external: ExternalUser): User
        return User(
            id = UserId(external.usr_id),
            email = Email(external.usr_email),
            tier = SupportTier.from(external.account_type)
        )

// UseCase работает только с моделью своего контекста
useCase.handle(userACL.translate(externalUser))
// ExternalUser никогда не попадает в Domain
```

## Context

Мотивация — в [`proposal.md`](./proposal.md), требования — в
[`specs/kit-installation/spec.md`](./specs/kit-installation/spec.md). Здесь фиксируются технические
решения по реализации.

Существенные для реализации свойства текущего окружения:

- Цель `init` выполняется **на хосте**, а не в контейнере: `make` внутри контейнера отсутствует.
  Значит, доступный инструментарий — то, что есть у пользователя на машине, и `ssh-keygen`
  становится новым предусловием установки.
- Цель `init` выполняется **до** `make build` и `make up`: контейнера и образа на этот момент
  ещё нет, поэтому генерация ключа контейнерными средствами невозможна.
- `.env` на этапе `init` заполнен не полностью: `GIT_HOST` и `CLAUDE_PROFILE` пользователь задаёт
  шагом позже. Цель `init` рассчитана на повторный запуск.
- Каталог `.ssh/` хоста монтируется в контейнер по пути `CONTAINER_SSH_DIR`
  (`/home/claude/.ssh`), см. `docker-compose.yml`. Пути внутри `.ssh/config` читает клиент SSH
  **внутри контейнера**, а не на хосте.
- `init` входит в белый список целей host-runner (`tools/host-runner/runner.py`,
  `ALLOWED_TARGETS`): цель может быть вызвана агентом из контейнера.
- `GIT_HOST` сейчас не потребляется ничем: переменная объявлена в `.env.example` и передаётся
  в контейнер, но ни один компонент её не читает. Конфигурация SSH становится её первым
  потребителем.

## Goals / Non-Goals

**Goals:**

- Реализовать подготовку SSH средствами самой цели `init`, не вводя отдельный скрипт установки.
- Сохранить цель неинтерактивной и повторно запускаемой: тот же принцип, что уже действует для `.env`.
- Дать `.ssh/config` пути, корректные с точки зрения контейнера, а не хоста.

**Non-Goals:**

- Проверка связи с git-хостом (`ssh -T`) и любая сетевая активность цели `init`.
- Ротация и удаление ключей, поддержка нескольких ключей и нескольких git-хостов в `.ssh/config`.
- Приведение прав доступа у файлов, которые цель не создавала.

## Decisions

### Решение 1. Генерация выполняется `ssh-keygen` на хосте

Пара создаётся вызовом `ssh-keygen -t ed25519 -f "$SSH_KEY" -N "" -C "<комментарий>"`.

Альтернативы:

- **Генерация внутри контейнера отдельной целью.** Отклонена: цель пришлось бы выполнять после
  `make build`, то есть подготовка окружения расщепилась бы на «до сборки» и «после сборки» —
  ровно та проблема, которую change устраняет.
- **Генерация средствами Python/OpenSSL.** Отклонена: добавляет зависимость тяжелее, чем
  `openssh-client`, который на машине с git по SSH и так практически всегда присутствует.

Отсутствие `ssh-keygen` обрабатывается как ошибка предусловия с внятным сообщением, а не как
молчаливый пропуск: молчаливый пропуск оставил бы пользователя с тем же пустым каталогом, что и
сегодня, но уже без указания, что делать.

### Решение 2. Значения читаются из `.env` тем же способом, что и в цели `shell`

`SSH_KEY`, `SSH_CONFIG`, `GIT_HOST`, `GIT_USER`, `CONTAINER_SSH_DIR` извлекаются из `.env`
через `sed -n 's/^ИМЯ=//p' .env | tail -n 1` с подстановкой умолчания, как это уже сделано в цели
`shell` для `CLAUDE_PROFILE` и `CLAUDE_ACCOUNTS_DIR`.

Альтернатива — `include .env` средствами `make` — отклонена: `.env` содержит значения, которые
`make` разберёт как свои переменные, а любая строка с пробелами или спецсимволами сломает разбор
всего `Makefile`, а не одной цели.

Умолчания при пустом значении берутся из `.env.example` (`SSH_KEY=.ssh/id_ed25519`,
`SSH_CONFIG=.ssh/config`, `GIT_USER=git`, `CONTAINER_SSH_DIR=/home/claude/.ssh`): цель должна
работать и в проекте, где пользователь урезал `.env`.

### Решение 3. `IdentityFile` указывает на путь внутри контейнера

`.ssh/config` читается клиентом SSH внутри контейнера, где каталог ключей смонтирован по
`CONTAINER_SSH_DIR`. Поэтому в `IdentityFile` подставляется `CONTAINER_SSH_DIR` + имя файла ключа
из `SSH_KEY`, а не хостовый путь `SSH_KEY`.

Хостовый путь в этом поле выглядел бы правдоподобно и не работал бы: внутри контейнера каталога
`.ssh` относительно домашнего каталога пользователя по такому пути нет. Это единственное место
change'а, где хостовое и контейнерное представление пути расходятся, — отсюда отдельное решение.

Запись конфигурации:

```text
Host <GIT_HOST>
  HostName <GIT_HOST>
  User <GIT_USER>
  IdentityFile <CONTAINER_SSH_DIR>/<имя файла из SSH_KEY>
  IdentitiesOnly yes
```

`IdentitiesOnly yes` добавляется намеренно: без него клиент перебирает все ключи, попавшие в
каталог, и git-сервис может отвергнуть соединение раньше, чем очередь дойдёт до нужного ключа.

### Решение 4. Идемпотентность проверяется по существованию файла

Признак «делать или не делать» — наличие приватного ключа по `SSH_KEY` и наличие файла по
`SSH_CONFIG`. Содержимое существующих файлов не разбирается и не сверяется с ожидаемым.

Альтернатива — сверять содержимое `.ssh/config` с эталоном и дописывать недостающую запись —
отклонена: это слияние конфигурации, а kit по действующему ограничению
([`README.md`](../../../README.md), раздел «Ограничения») слияния файлов не выполняет нигде.

### Решение 5. Пустой `GIT_HOST` — предупреждение, а не ошибка

Порядок установки ставит `make init` (шаг 2) **раньше** заполнения `.env` (шаг 3), поэтому при
первом запуске `GIT_HOST` заведомо пуст. Прерывание цели ошибкой сломало бы штатный порядок
установки. Цель создаёт ключ, пропускает конфигурацию и печатает, что после заполнения `GIT_HOST`
нужно выполнить `make init` повторно.

Генерация ключа от `GIT_HOST` не зависит и выполняется в обоих случаях.

### Решение 6. Права выставляются явным `chmod`

`ssh-keygen` создаёт приватный ключ с `600` сам, но `umask` пользователя влияет на публичный ключ
и на создаваемый целью `.ssh/config`. Права выставляются явно: `600` — приватный ключ, `644` —
публичный ключ и `.ssh/config`. Существующие файлы не трогаются: их права — зона ответственности
владельца.

## Risks / Trade-offs

- **Ключ без passphrase лежит на диске в открытом виде.** → Осознанный размен, зафиксирован
  в `proposal.md`. Смягчение: `.ssh/` исключён из репозитория записью в `.gitignore`, права
  `600`, ключ отдельный для проекта — компрометация не затрагивает личный ключ пользователя.
- **`init` доступен агенту через host-runner.** → Агент может вызвать генерацию ключа на хосте.
  Смягчение: цель идемпотентна и существующий ключ не заменяет, поэтому повторный вызов не отбирает
  доступ; приватный ключ цель не печатает — в вывод идёт только публичный.
- **Пользователь ожидает, что ключ уже зарегистрирован в git-сервисе.** → Сгенерированный ключ
  git-сервису неизвестен, и первый push из контейнера завершится отказом. Смягчение: цель печатает
  публичный ключ с прямым указанием добавить его в git-сервис; шаг 4 `README.md` переписывается
  на регистрацию ключа вместо копирования.
- **`ssh-keygen` отсутствует на хосте.** → Цель завершится ошибкой на новой зависимости.
  Смягчение: `openssh-client` добавляется в перечень предусловий `README.md`, сообщение об ошибке
  называет недостающую утилиту.
- **`.ssh/config` создан для одного хоста.** → Проект, работающий с двумя git-сервисами, потребует
  ручной правки файла. Смягчение: файл создаётся один раз и повторными запусками не переписывается,
  поэтому ручная правка сохраняется.

## Context

Мотивация — в [proposal.md](./proposal.md), раздел «Why». Здесь фиксируется техническая сторона.

Исходное состояние: `docker-compose.yml` содержит секцию `build` и ссылается на тег `claude-openspec:local`,
цель `make build` выполняет `docker compose --profile claude build claude`, `Dockerfile` входит
в `PAYLOAD_PATHS` установщика, каталога `.github/` в репозитории нет. Образ надстраивает базовый
`ghcr.io/united-software-platform/claude:latest` тремя инструментами: утилитой OpenSpec (`ARG OPENSPEC_VERSION`),
интерпретатором Python через uv (`ARG PYTHON_VERSION`) и самим uv (`ARG UV_VERSION`).

Ограничения, формирующие подход:

- В организации уже есть работающий образец — пайплайн `docker-claude.yml` репозитория базового образа:
  задания `resolve` → `check` (матрица архитектур) → `push`, публикация в GHCR встроенным токеном,
  ежедневная пересборка. Пользователь выбрал повторить именно его.
- Незаархивированный change `add-repo-versioning` вводит инкрементацию `VERSION` и git-теги `vX.Y.Z`.
  Файл `VERSION` существует уже сейчас, поэтому пайплайн может читать его немедленно, но пока значение
  неподвижно.
- Установщик копирует файлы поставки дословно, сохраняя пути (`kit-installation`, требование «Структура
  установки повторяет структуру kit'а»), — подстановка значений в файлы поставки на этапе установки
  недоступна.
- Правила проекта запрещают автоматические коммиты и push ([GIT-015](../../../rules/git-rules.md#коммиты-и-push)),
  поэтому пайплайн ничего не коммитит в репозиторий.

## Goals / Non-Goals

**Goals:**

- Один опубликованный мультиарх-образ, пригодный к запуску в любом установленном проекте без локальной сборки.
- Плановая пересборка, приносящая обновления базового образа и инструментов без правки исходника.
- Проверка образа до публикации, достаточная для пересборки без участия человека.
- Возможность закрепить версию образа в конкретном проекте, не редактируя файлы поставки.

**Non-Goals:**

- Публикация образа в другие реестры, кроме GHCR.
- Подписи образа и SBOM: отдельная задача, не требующаяся для отказа от локальной сборки.
- Автоматическое обновление образа в уже запущенных контейнерах.
- Собственная нумерация образа, независимая от версии kit'а.

## Decisions

### Реестр и имя образа

GHCR, имя `ghcr.io/<владелец>/<репозиторий>` в нижнем регистре, вычисляемое из координат репозитория
в момент запуска пайплайна.

Почему так: публикация выполняется встроенным токеном рабочего процесса — отдельных учётных данных
заводить не нужно, и организация уже публикует туда базовый образ. Вычисление имени из `GITHUB_REPOSITORY`
исключает расхождение имени образа с репозиторием-исходником; приведение к нижнему регистру обязательно,
так как путь GHCR заглавных букв не допускает, а владелец репозитория их содержать может.

Отвергнуто: Docker Hub — требует долгоживущего секрета в настройках репозитория; жёстко записанное имя
образа в пайплайне — расходится с репозиторием при переносе или переименовании.

### Структура пайплайна: три задания

`resolve` (расчёт имени образа и версий инструментов) → `check` (матрица `linux/amd64`, `linux/arm64`) →
`push` (сборка мультиарх-манифеста и публикация).

Почему так: мультиплатформенный образ нельзя целиком загрузить в локальный демон Docker, поэтому проверка
запуском возможна только по одной архитектуре за раз; отдельные задания матрицы дают параллельность и
не позволяют медленной эмулированной сборке arm64 задерживать amd64. Расчёт версий вынесен в отдельное
задание, чтобы проверка и публикация пользовались одним и тем же значением: рассчитай версию дважды —
и опубликованным окажется не то, что проверено.

`push` выполняется с `cache-from` обеих архитектур, поэтому повторно слои не собираются.

Отвергнуто: одно задание со сборкой и публикацией сразу — проверка запуском становится невозможной для
второй архитектуры, а публикация непроверенного образа противоречит требованию «Публикация только после
проверки образа».

### Теги образа: версия kit'а и `latest`

Публикуются два тега: значение файла `VERSION` и `latest` (только при сборке из основной ветки).

Почему так: у образа нет собственной сущности, отдельной от kit'а, — он существует ради поставки, поэтому
его метка версии совпадает с версией kit'а. Это же решение связывает образ с ключом установщика `--ref`:
установка по тегу `vX.Y.Z` и образ с тегом `X.Y.Z` описывают одно состояние поставки. Пока
`add-repo-versioning` не реализован, `VERSION` неподвижен и тег версии совпадает с `1.0.0` — работоспособности
это не мешает, потому что рабочий тег по умолчанию `latest`.

Из этого следует состав path-фильтра триггера: кроме исходника образа и файла пайплайна в него входит
`VERSION`. Иначе инкрементация версии не порождала бы образ с соответствующим тегом, и закрепление
`SDD_KIT_IMAGE_TAG=X.Y.Z` для части версий указывало бы в пустоту.

Отвергнуто: тег по версии OpenSpec — базовый репозиторий тегирует образ версией Claude Code, потому что
там образ и есть этот инструмент; здесь инструментов несколько, и ни один не представляет образ целиком.
Отвергнуто: тег по SHA коммита — не связан с тем, что пользователь видит в `--ref` и в бейдже версии.

### Версия OpenSpec разрешается при сборке в пределах мажорной

`resolve` получает конкретную версию по диапазону мажорной (`npm view "@fission-ai/openspec@^1" version`)
и передаёт её build-arg'ом в сборку; `check` сверяет `openspec --version` в образе с этим значением.

Почему так: плановая пересборка имеет смысл, только если состав инструментов действительно обновляется,
а полное закрепление версии в `ARG` этого не даёт. Граница мажорной версии оставлена намеренно: комментарий
в `Dockerfile` уже фиксирует, что несовместимая мажорная версия ломает скиллы `openspec-*` из состава поставки.
Разрешение выполняется в `resolve` один раз и потому одинаково в проверке и в публикации.

`ARG OPENSPEC_VERSION` в `Dockerfile` сохраняется со значением по умолчанию: локальная сборка образа
разработчиком не должна зависеть от сети npm-реестра сверх необходимого. Значение по умолчанию и мажорная
граница пайплайна — два места, которые могут разойтись; расхождение обнаруживает `check`, сверяющий
разрешённую версию с мажорной границей до сборки.

Версии Python и uv остаются закреплёнными полностью: они задают среду выполнения проекта, и их смена —
осознанная правка, а не побочный результат пересборки.

Отвергнуто: разрешение без границы (`latest`) — впускает несовместимый мажорный выпуск в образ автоматически.
Отвергнуто: сохранение полного закрепления — обесценивает плановую пересборку для главного инструмента kit'а.

### Триггеры пересборки

`push` в основную ветку и `pull_request` с path-фильтром (`Dockerfile`, `VERSION`, файл пайплайна),
`schedule` раз в сутки и `workflow_dispatch`.

Почему так: содержимое образа зависит от внешних источников — базового образа `claude:latest` и npm-реестра, —
и коммитами эти обновления не сопровождаются. Расписание — единственный триггер, который их ловит. Время
запуска смещено от круглого часа: на нулевой минуте очередь раннеров перегружена. Path-фильтр исключает
пересборку на правках правил и документации, которые образа не касаются.

### Ссылка на образ в поставке и способ закрепления

`docker-compose.yml` ссылается на `${SDD_KIT_IMAGE:-ghcr.io/united-software-platform/sdd-developer-kit}:${SDD_KIT_IMAGE_TAG:-latest}`,
секция `build` удаляется. Обе переменные добавляются в `.env.example`.

Почему так: файлы поставки копируются дословно, поэтому тег конкретной версии нельзя подставить при установке —
значением по умолчанию остаётся `latest`. Закрепление версии выполняется пользователем в `.env`, то есть
без правки файла поставки, и переживает повторную установку kit'а. Подмена имени образа той же парой
переменных закрывает сценарий собственной сборки.

Отвергнуто: подстановка версии установщиком в `docker-compose.yml` — нарушает дословность копирования
и делает установленный файл отличным от файла поставки при каждой проверке перезаписи.
Отвергнуто: `latest` без возможности переопределения — лишает пользователя воспроизводимости.

### Обновление образа при `make up`

Отдельной цели получения образа не заводится (решение пользователя). `make up` перед запуском пытается
обновить образ и не прерывается, если реестр недоступен: неуспешное обновление печатает предупреждение,
а запуск продолжается на локально доступном образе.

Почему так: без попытки обновления проект, однажды загрузивший `latest`, никогда не увидел бы результатов
плановой пересборки — тег `latest` в локальном кэше не обновляется сам. Жёсткое требование обновления
(`--pull always`) сделало бы запуск невозможным без сети даже при уже загруженном образе, что противоречит
требованию «Поведение при недоступности реестра». Мягкая попытка удовлетворяет оба сценария: первый запуск
без образа завершается ошибкой получения образа, повторный запуск без сети работает.

Отвергнуто: `pull_policy: always` в конфигурации окружения — тот же отказ при отсутствии сети, но без
возможности отличить его от отсутствия образа.

### Права пайплайна

`packages: write` объявляется только в задании публикации, `resolve` и `check` работают с `contents: read`.
Публикация не выполняется для событий `pull_request`.

Почему так: запрос на слияние из форка не должен получать доступ на запись в реестр организации, а задание,
которому запись не нужна, не должно её иметь.

## Risks / Trade-offs

- [Плановая пересборка публикует новый состав инструментов под прежним тегом версии] → тег версии не даёт
  побайтовой неизменности; сценарий, которому нужна неизменность, адресует образ по digest — ограничение
  зафиксировано в спецификации и в `README.md`.
- [Новый минорный выпуск OpenSpec ломает скиллы `openspec-*`] → мажорная граница ограничивает диапазон,
  `check` останавливает публикацию при неработоспособной утилите; пострадавший проект закрепляет предыдущий
  тег или digest в `.env` до исправления. Полностью риск не снимается: проверка убеждается, что утилита
  запускается, но не прогоняет скиллы.
- [Пакет GHCR по умолчанию наследует приватность и не читается анонимно] → видимость пакета переключается
  в настройках пакета вручную после первой публикации; шаг вынесен в задачи, так как выполняется вне
  репозитория и пайплайном не автоматизируется.
- [Ежедневная сборка arm64 идёт через эмуляцию QEMU и занимает десятки минут] → кэш слоёв по архитектурам
  и `concurrency` с отменой предыдущих запусков; для публичного репозитория минуты раннеров не тарифицируются.
- [В проектах, где kit уже установлен, остаётся осиротевший `Dockerfile`] → файл перестаёт использоваться,
  так как `docker-compose.yml` на него не ссылается; повторная установка его не удаляет — установщик файлов
  не удаляет вовсе. Упоминание в `README.md` о том, что файл можно удалить вручную, закрывает вопрос.
- [Первый запуск контейнера требует сети — раньше сеть была нужна только на установку] → зафиксировано
  требованием «Поведение при недоступности реестра»; альтернативы нет, это следствие отказа от локальной сборки.
- [Пайплайн и `add-repo-versioning` добавляют файлы в один каталог `.github/workflows/`] → файлы независимы;
  утверждение того change'а «первый пайплайн в репозитории» становится неточным и подлежит правке при его
  доработке, конфликта в коде нет.

## Migration Plan

1. Пайплайн добавляется и запускается вручную (`workflow_dispatch`) до правки файлов поставки: пока образ
   не опубликован и не проверен, переключать `docker-compose.yml` нельзя — установка сломалась бы.
2. После успешной публикации видимость пакета GHCR переключается на публичную, доступность проверяется
   загрузкой образа без аутентификации.
3. Затем переключаются файлы поставки: `docker-compose.yml`, `Makefile`, `.env.example`, `install.sh`,
   белый список host-runner, `README.md`.
4. Откат: возврат секции `build` и цели `make build`; `Dockerfile` из репозитория не удаляется ни на одном
   шаге, поэтому откат не требует восстановления файлов.

## Why

Сейчас порядок подготовки рабочего окружения (сборка Docker-образа, монтирование профиля аккаунта,
запуск раннера целей `make` на хосте, готовность контейнера к работе с Claude Code и OpenSpec) нигде
не зафиксирован как единая последовательность шагов. Он восстанавливается по отдельности из
`Dockerfile`, `docker-compose.yml` и `tools/host-runner/README.md`. Это делает старт разработчика
и CI невоспроизводимым и зависящим от того, кто и как когда-то уже проходил этот путь вручную.

## What Changes

- Формализован canonical порядок бутстрапа: подготовка `.env` из `.env.example` → сборка образа
  (`docker compose --profile claude build claude`) → запуск контейнера с профилем аккаунта
  (`CLAUDE_PROFILE`, `docker compose --profile claude up -d --force-recreate claude`) → готовность
  к рабочей сессии агента.
- Зафиксированы предусловия старта: `.env` с обязательными переменными окружения, SSH-ключ в
  `${SSH_DIR:-.ssh}` для доступа к git-репозиторию, отдельный каталог профиля аккаунта в
  `${CLAUDE_ACCOUNTS_DIR:-.claude-accounts}/${CLAUDE_PROFILE}`.
- Описан опциональный шаг — запуск `tools/host-runner/runner.py` на хосте, когда агенту внутри
  контейнера нужны цели `make` (`init`, `up`, `down`, `restart`, `logs`, `authors`, `scan`) без
  доступа к Docker-сокету.
- Зафиксировано, что бутстрап выполняет либо разработчик вручную, либо CI — последовательность шагов
  одна и та же, различается только среда выполнения команд `docker compose`.

## Capabilities

### New Capabilities

- `repo-bootstrap`: сборка образа, запуск контейнера с профилем аккаунта и (опционально) host-runner
  на хосте — последовательность действий до начала рабочей сессии в контейнере.

### Modified Capabilities

(нет — существующих capability в `openspec/specs/` ещё не было)

## Impact

- Затронуты как контекст, а не как правки кода: `Dockerfile`, `docker-compose.yml`, `.env.example`,
  `tools/host-runner/*`. Их поведение уже существует — спецификация фиксирует его, не меняя.
- `CLAUDE.md` и `AGENTS.md` ссылаются на `README.md` в корне репозитория, которого сейчас нет.
  Требуется ли создать этот файл как часть бутстрап-документации — решается в `design.md`/`tasks.md`.

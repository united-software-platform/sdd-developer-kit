# Разработка SDD Developer Kit

Документ для тех, кто правит сам набор: устройство репозитория, локальные проверки, сборка образа
окружения агента, блок бейджей и порядок выпуска версии. Пользователю набора он не нужен —
инструкция по применению живёт в [`README.md`](./README.md).

## Устройство репозитория

Репозиторий kit'а сам развёрнут теми же инструментами: правила лежат в [`rules/`](./rules),
процесс ведётся через OpenSpec в [`openspec/`](./openspec), установщик — [`install.sh`](./install.sh).
Правила работы с репозиторием описаны в [`CLAUDE.md`](./CLAUDE.md) и [`AGENTS.md`](./AGENTS.md).

Состав поставки — то, что установщик копирует в чужой проект, — задан переменной `PAYLOAD_PATHS`
в [`install.sh`](./install.sh); установщик её единственный читатель. Этот документ в поставку
не входит: в установленном проекте он описывал бы чужой репозиторий.

## Локальные проверки

Собственные проверки репозитория лежат в [`tools/`](./tools) и запускаются локально до отправки
изменений — тот же вердикт даёт пайплайн:

```bash
sh tools/make-lint/check.sh                 # объём секций Makefile, предел по умолчанию — 30 строк
sh tools/make-lint/check.sh --max-lines 40  # другой предел
```

Секцией считается цель целиком: непрерывный блок комментария перед строкой цели, сама строка цели
и её рецепт. Коды возврата — `0` (пройдено), `1` (есть секции сверх предела), `2` (ошибка вызова
или окружения). Проверки в состав поставки не входят: установленный проект ведёт свой `Makefile`
по собственным правилам.

## Образ окружения агента

Образ публикуется в GitHub Container Registry (GHCR) под именем
`ghcr.io/united-software-platform/sdd-developer-kit`, тегами — версия kit'а из [`VERSION`](./VERSION)
и `latest`, мультиарх: `linux/amd64` и `linux/arm64`. Исходник — [`Dockerfile`](./Dockerfile);
пользовательская сторона (закрепление тега, поведение без сети) описана в
[`README.md`](./README.md#образ-окружения-агента).

Собирает и публикует образ сценарий `docker-agent` в GitHub Actions. Публикации всегда предшествует
проверка: образ собирается отдельно под каждую архитектуру, и в нём запускаются все инструменты —
если хоть один не отвечает версией, в реестр не попадает ничего.

Пересборка запускается при выпуске новой версии kit'а, при правке `Dockerfile` или `VERSION`
в основной ветке, раз в сутки по расписанию и вручную. Суточная пересборка нужна потому, что состав
образа зависит от внешних источников: базовый образ и пакеты инструментов обновляются вне
репозитория, и коммитами такие обновления не сопровождаются. Версия OpenSpec при этом разрешается
в пределах закреплённого мажорного разряда, а версии Python и uv остаются закреплёнными полностью —
их смена меняет среду выполнения проекта и делается правкой `Dockerfile`.

Сборку выпущенной версии запускает сам релизный сценарий: коммит с новым `VERSION` он публикует
встроенным токеном рабочего процесса, а изменения от такого токена сборку не запускают — связь
«поднялся `VERSION` — пересобрался образ» для релиза приходится задавать явно.

Из какой версии kit'а собран уже загруженный образ, показывает его метка — сверять имя тега
с [`VERSION`](./VERSION) вручную не нужно:

```bash
docker image inspect ghcr.io/united-software-platform/sdd-developer-kit:latest \
    --format '{{index .Config.Labels "org.opencontainers.image.version"}}'
```

Рядом с ней образ несёт `org.opencontainers.image.revision` — SHA коммита, из которого он собран,
и `org.opencontainers.image.source` — адрес репозитория-исходника.

> **Внимание:** релиз сборку образа запускает, но её результата не ждёт — сборка arm64 идёт через
> эмуляцию и занимает десятки минут. До её завершения тега новой версии в реестре нет, а `latest`
> указывает на образ предыдущей версии. Неуспех сборки виден по прогону `docker-agent`,
> а не по результату релиза.

## Блок бейджей

Блок бейджей стоит в [`README.md`](./README.md) между заголовком файла и назначением. Пять бейджей
из шести динамические: значение вычисляется из файла репозитория на стороне `shields.io`, ручных
копий версий в документе нет. Правка источника меняет бейдж без правки `README.md` — и наоборот,
переименование `ARG` ломает бейдж молча.

| Бейдж | Источник значения |
|-------|-------------------|
| `claude image` | строка `FROM` в [`Dockerfile`](./Dockerfile) |
| `python` | `ARG PYTHON_VERSION` в [`Dockerfile`](./Dockerfile) |
| `openspec` | `ARG OPENSPEC_VERSION` в [`Dockerfile`](./Dockerfile) |
| `uv` | `ARG UV_VERSION` в [`Dockerfile`](./Dockerfile) |
| `version` | файл [`VERSION`](./VERSION) |
| `license` | статическое значение, источника в репозитории нет |

Ограничения блока:

- **значения читаются из ветки `main`.** Бейдж показывает состояние основной ветки, а не той,
  в которой открыт документ: в ветке разработки он покажет ещё не изменённое значение;
- **репозиторий должен быть доступен анонимно.** `shields.io` ходит за исходником без
  аутентификации; в закрытом репозитории динамические бейджи перестают отображать значение,
  и их приходится заменять статическими;
- **переименование `ARG` или `FROM` ломает бейдж молча.** Проверки, связывающей запрос бейджа
  с содержимым `Dockerfile`, нет — после правки исходника бейджи нужно открыть глазами.

Абсолютные URL в блоке допускаются исключением
[DOC-015](./rules/documentation-rules.md#ссылки-doc-015): цель ссылки внешняя — сервис бейджей,
реестр образов, страница пакета.

## Версия репозитория

Версия ведётся по Semantic Versioning 2.0.0 и хранится в двух носителях. Файл [`VERSION`](./VERSION) —
единственный источник истины: он содержит номер без префикса (`1.0.0`), его читает установщик
и записывает в манифест установки, из него же берёт значение бейдж версии. Аннотированный git-тег
`vX.Y.Z` — публикуемая метка того же номера: на него ссылается ключ `--ref` установщика, когда нужна
воспроизводимая установка конкретной ревизии.

Версия повышается, когда изменяется состав поставки — то, что установщик копирует в чужой проект.
Перечень таких путей задан переменной `PAYLOAD_PATHS` в [`install.sh`](./install.sh).

Релиз выполняется одним запуском сценария `release` в GitHub Actions — «Run workflow» с единственным
параметром:

| Параметр | Значение |
|----------|----------|
| `bump` | разряд: `major` — несовместимое изменение состава поставки, `minor` — новая возможность с сохранением совместимости, `patch` — исправление или правка документации |

Прогон поднимает `VERSION`, коммитит изменение, ставит аннотированный тег `vX.Y.Z`, публикует его
и запускает сборку образа выпущенной версии — см. [Образ окружения агента](#образ-окружения-агента).
Локальной команды инкрементации нет: файл, коммит и тег появляются одним действием, поэтому разойтись
между собой они не могут.

Заголовок релизного коммита — `Релиз vX.Y.Z`, без кода и номера задачи: кода у сценария нет, а
выводить его из контекста запрещает [GIT-010](./rules/git-rules.md#формат-сообщения-коммита). Такой
коммит описан в правилах как именованное исключение
[GIT-021](./rules/git-rules.md#исключение-для-машинного-релизного-коммита) — оно действует только для
коммита релизного сценария, меняющего один файл `VERSION`. Перед записью прогон проверяет, что
в `VERSION` нет незакоммиченных правок — гейт [GIT-020](./rules/git-rules.md#гейт-редактирования).

Ограничения механизма:

- о пропущенном релизе ничто не напоминает: состав поставки может измениться в `main` без повышения
  версии, и обнаружится это при следующей установке, а не проверкой. Решение о выпуске принимает
  человек — автоматической страховки под ним нет;
- разряд выбирает человек: разметка артефактов процесса не различает несовместимые изменения внутри
  изменённого требования, поэтому автоматический вывод разряда занижал бы его именно там, где ошибка
  дороже всего;
- механизм принадлежит этому репозиторию: `VERSION` и сценарий `release` в состав поставки не входят
  и в сценарии OpenSpec не встраиваются — иначе в установленном проекте инструкция оказалась бы
  невыполнимой.

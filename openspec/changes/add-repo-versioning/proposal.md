## Why

Репозиторий поставляет kit в чужие проекты одной удалённой командой, но не сообщает, какую именно
ревизию проект получил: файл `VERSION` заведён со значением `1.0.0` и с тех пор не менялся, git-тегов
нет вовсе, а ключ установщика `--ref` не имеет ни одного тега, на который можно сослаться ради
воспроизводимой установки. Манифест `.sdd-kit-manifest.json` записывает `kit_version` из файла, поэтому
неподвижная версия делает поле бессмысленным: два разных состояния поставки помечаются одинаково.

Ручная правка `VERSION` эту проблему не решает — шаг, не привязанный к событию процесса, забывается.
Нужен носитель версии, событие, при котором она обязана измениться, и проверка, замечающая пропуск.
Само событие при этом должно оставаться одним действием человека: чем больше вокруг него обрядов,
тем вероятнее, что его пропустят.

## What Changes

- Вводится версионирование репозитория по Semantic Versioning 2.0.0 с исходной версией `v1.0.0`.
  Носитель истины — файл `VERSION` (номер без префикса), публикуемая метка — аннотированный git-тег
  `vX.Y.Z`.
- Релиз выполняется одним запуском вручную запускаемого сценария GitHub Actions (`workflow_dispatch`)
  с двумя параметрами: разряд (`major`, `minor`, `patch`) и код задачи. Сценарий поднимает `VERSION`,
  создаёт коммит, ставит аннотированный тег `vX.Y.Z` и публикует его. Локального скрипта инкрементации
  нет: прибавление единицы к номеру в файле из одной строки не требует собственного инструмента.
- Разряд задаёт человек — параметром запуска. Автоматический вывод разряда и привязка к шагу архивации
  change не вводятся: и то, и другое потребовало бы править файлы, уезжающие в целевые проекты.
- Код задачи тоже задаёт человек: сообщение релизного коммита обязано соответствовать
  [GIT-009](../../../rules/git-rules.md#формат-сообщения-коммита), а выводить номер задачи «по смыслу»
  запрещает [GIT-010](../../../rules/git-rules.md#формат-сообщения-коммита).
- Добавляется проверка в GitHub Actions: изменение путей поставки без инкрементации `VERSION` завершает
  пайплайн ошибкой. Сверка тега с содержимым `VERSION` отдельной проверкой не нужна — оба носителя
  меняются одним запуском релизного сценария, поэтому разойтись не могут.
- Список путей поставки выносится из переменной `PAYLOAD_PATHS` в `install.sh` в отдельный файл
  `payload.txt`. Установщик и проверка читают один и тот же файл построчно, без разбора шелл-переменной.
- Бейдж версии в `README.md` показывает значение с префиксом `v` (`v1.0.0` вместо `1.0.0`), сохраняя
  файл `VERSION` источником значения.

## Capabilities

### New Capabilities

- `repo-versioning`: формат версии репозитория, носители версии и их согласованность, релизный
  сценарий и его параметры, границы автоматизации git-операций, проверка пропущенной инкрементации.

### Modified Capabilities

- `readme-badges`: бейдж версии kit'а показывает номер с префиксом `v`, единообразно с git-тегом.

## Impact

- Новые файлы: `payload.txt` (список путей поставки), `tools/version/check.sh` (проверка),
  `.github/workflows/` — два сценария: проверка на `pull_request` и `push`, релиз по `workflow_dispatch`.
  CI в репозитории сейчас отсутствует, оба вводятся с нуля.
- Изменяемые файлы: `VERSION` (при каждом релизе — сценарием, а не руками), `install.sh` (список путей
  поставки читается из `payload.txt` вместо переменной), `README.md` (бейдж версии, раздел о
  версионировании в части «Разработка самого kit'а»).
- Не затрагивается: ни один файл из состава поставки. `install.sh` продолжает читать `VERSION` как
  номер без префикса; сам установщик, `payload.txt` и релизный сценарий в целевой проект не копируются,
  сценарии OpenSpec не правятся — установленные проекты о версионировании kit'а не узнают.

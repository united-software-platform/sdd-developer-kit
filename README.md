Изолированное окружение для Spec-Driven Development (SDD): Claude Code и OpenSpec в контейнере, правила
репозитория и инструменты SDD — в вашем проекте одной командой. Здесь — путь от установки до первой сессии
агента; другие задачи — в [документе кейсов](./docs/use-cases.md), правка набора — в [`CONTRIBUTING.md`](./CONTRIBUTING.md).

## Что нужно

- Docker с плагином Compose и `make`.
- `ssh-keygen` (пакет `openssh-client`) и `curl` или `wget`.
- Доступ в интернет: установщик загружается с GitHub, а образ окружения агента — из реестра
  при первой подготовке проекта. Дальше сеть нужна только для обновления образа.

---

## Шаг 1. Установить набор

Внутри контейнера окажутся инструменты образа окружения агента:

- [claude](https://github.com/united-software-platform/claude) — образ окружения: агент Claude Code
  работает в контейнере, видит только каталог проекта и ходит в git под отдельным аккаунтом
  и SSH-ключом.
- [OpenSpec](https://github.com/Fission-AI/OpenSpec) — ведёт Spec-Driven Development: его
  командами `/opsx:*` агент создаёт change-артефакты и спецификации в `openspec/`.
- [Python](https://www.python.org) — расширяет возможности агента: на нём агент пишет и запускает
  собственные скрипты и инструменты внутри контейнера.
- [uv](https://github.com/astral-sh/uv) — менеджер зависимостей для Python; им же в образ поставлен
  сам интерпретатор.

В репозитории вашего проекта появится:

- Окружение агента — `docker-compose.yml`, `Makefile`, `.env.example`: контейнер поднимается
  и обслуживается целями `make`.
- [Правила репозитория](./rules) — `rules/`, `CLAUDE.md`, `AGENTS.md`: нормы документации,
  терминологии, чтения, `Makefile` и Git, которые агент читает перед задачей.
- [host-runner](./tools/host-runner) — `tools/host-runner/`: позволяет агенту запускать цели `make`
  на вашей машине. Без него агент видит только исходники; ставится по желанию.
- [make-lint](./tools/make-lint) — `tools/make-lint/`: проверяет объём секций `Makefile` по норме
  из правил репозитория; запускается командой `sh tools/make-lint/check.sh` перед отправкой изменений.
- [Навык документов проекта](./.claude/skills/project-docs) — `.claude/skills/project-docs/`: по просьбе
  агент проверяет `README.md`, `CONTRIBUTING.md` и документ кейсов по норме из правил репозитория
  и заводит недостающие по образцам. В отличие от skills SDD, приходит с установкой, а не из `openspec init`.
- Skills и команды SDD — `.claude/skills/openspec-*/`, `.claude/commands/opsx/`, `openspec/`: рабочие
  процессы `/opsx:*`; их разворачивает `make init` на шаге 2 вызовом `openspec init`.
- Манифест установки — `.sdd-kit-manifest.json`: по нему повторная установка отличает ваши правки
  от нетронутых файлов набора.

Версии инструментов показывают бейджи в начале файла. Версии Python и uv закреплены
в [`Dockerfile`](./Dockerfile), версия набора — в [`VERSION`](./VERSION); выпуски Claude Code
и OpenSpec в загруженном образе показывают его метки. Пайплайны репозитория набора в проект
не попадают: сценарии непрерывной интеграции проект ведёт сам, а проверки самого набора описаны
в [`CONTRIBUTING.md`](./CONTRIBUTING.md#проверки).

В корне своего проекта выполните:

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh | sh
```

Установщик ничего не пишет, пока не покажет план: файлы к созданию, к обновлению и к перезаписи.
Если какие-то файлы набора в проекте уже есть, он спросит подтверждение перед их перезаписью.

Подробнее — [кейс 1](./docs/use-cases.md#кейс-1-хочу-прочитать-установщик-до-запуска).

## Шаг 2. Подготовить проект

```bash
make init
```

Цель создаёт `.env` из шаблона, каталоги `.ssh/` и `.claude-accounts/` и дописывает их в `.gitignore`,
чтобы секреты не попали в репозиторий. Затем готовит SSH: генерирует ключ `ed25519` без passphrase
по пути из `SSH_KEY` и печатает публичный ключ. Конфигурацию `.ssh/config` цель создаёт по
заполненному `GIT_HOST` — на этом шаге он ещё пуст, поэтому цель сообщает о повторном запуске.

Последним шагом цель разворачивает инструменты SDD: выполняет `openspec init` в контейнере агента
и создаёт `.claude/skills/openspec-*/`, `.claude/commands/opsx/` и каталог `openspec/` версией утилиты
из образа. Если образа ещё нет, он загружается из реестра, поэтому первый запуск занимает время загрузки.

Существующие `.env`, ключ, `.ssh/config`, `openspec/config.yaml`, `openspec/changes/` и `openspec/specs/`
цель не трогает — обновляются только skills и команды OpenSpec, — поэтому вы можете запускать её повторно.

> **Внимание:** шаг требует запущенного Docker и доступа в сеть: образ окружения загружается
> из реестра. Хостовая часть — `.env`, каталоги, SSH-ключ и `.ssh/config` — выполняется до вызова
> контейнера, поэтому при недоступном Docker её результат сохраняется, а цель завершается ошибкой
> на шаге `openspec init`.

## Шаг 3. Заполнить .env

Откройте `.env` и задайте обязательные значения:

- `GIT_HOST` — хост git-сервиса, например `github.com`; по нему `make init` создаст `.ssh/config`;
- `CLAUDE_PROFILE` — имя каталога вашего профиля аккаунта, например `alex`. Этой переменной нет
  в шаблоне: значение своё у каждого разработчика, поэтому добавьте строку `CLAUDE_PROFILE=<профиль>`
  сами.

У остальных переменных есть значения по умолчанию, полный их состав — в [`.env.example`](./.env.example).
Переменные, нужные только для отдельной задачи — закрепления образа или host-runner, — называют
кейсы этих задач.

> **Важно:** контейнер видит только каталог профиля, заданного `CLAUDE_PROFILE`. Без этой
> переменной монтируется несуществующий каталог — так сделано намеренно, чтобы агент не получил
> доступ к чужим профилям.

## Шаг 4. Зарегистрировать ключ и создать профиль

```bash
make init
mkdir -p .claude-accounts/$(sed -n 's/^CLAUDE_PROFILE=//p' .env)
```

Повторный `make init` создаёт `.ssh/config`: `GIT_HOST` теперь заполнен. Публичный ключ он уже
не печатает — вывод даётся один раз, при создании ключа на шаге 2, поэтому выведите его заново:

```bash
cat .ssh/id_ed25519.pub
```

Добавьте этот ключ в git-сервис. Он сгенерирован для проекта и сервису пока неизвестен — без
регистрации push из контейнера не пройдёт.

## Шаг 5. Запустить агента

```bash
CLAUDE_PROFILE=<профиль> docker compose run --rm claude
```

Рабочая сессия — контейнер, который создаётся на запуске и удаляется на выходе из агента. Собирать
ничего не нужно: образ окружения загружается из реестра, и первый запуск занимает время загрузки.

Внутри доступны Claude Code и OpenSpec: `openspec status`, `/opsx:propose` и остальные команды.

Если агент при запуске просит авторизацию заново, `CLAUDE_PROFILE` указывает на каталог, которого нет:
проверьте имя и наличие каталога в `.claude-accounts/`.

Подробнее — [кейс 3](./docs/use-cases.md#кейс-3-хочу-работать-в-проекте-под-несколькими-аккаунтами).

## Ограничения

- **Установка требует сети и публичного репозитория.** Работа в закрытом контуре и установка из
  приватного репозитория не поддерживаются; обходной путь — `--source` с локальной копией набора,
  см. [кейс 2](./docs/use-cases.md#кейс-2-хочу-установить-конкретную-ревизию-набора-или-поставить-его-без-сети).
- **Слияния файлов нет.** Конфликт разрешается перезаписью целиком: свои цели `Makefile` или разделы
  `CLAUDE.md` перенесите вручную после установки.
- **Собственный `.claude/skills/project-docs/` проекта конфликтует с навыком набора.** Его файлы
  попадают в перечень перезаписи и после подтверждения заменяются навыком набора; свой навык
  с этим именем переименуйте до установки.
- **Сбой во время записи оставляет проект частично установленным.** Транзакционного отката нет;
  признак незавершённой установки — отсутствующий или неполный манифест, лечение — повторный запуск.
- **Умолчание `main` невоспроизводимо во времени.** Для повторяемой установки указывайте `--ref`
  с тегом или коммитом.
- **Пути поставки без пробелов.** Список путей и манифест разбираются построчно.

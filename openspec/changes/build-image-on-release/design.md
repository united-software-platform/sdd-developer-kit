## Context

Мотивация — в [proposal.md](./proposal.md), раздел «Why»; требования — в дельтах
[`agent-image`](./specs/agent-image/spec.md) и [`repo-versioning`](./specs/repo-versioning/spec.md).

Существенные для решения свойства текущего устройства:

- `release.yml` — единственный запускаемый вручную сценарий; он пишет `VERSION`, коммитит, ставит
  аннотированный тег и публикует оба встроенным `GITHUB_TOKEN`;
- `docker-agent.yml` состоит из трёх заданий: `resolve` (имя образа, версия kit'а из `VERSION`,
  версия OpenSpec), `check` (сборка и запуск инструментов по одной архитектуре, `load: true`)
  и `push` (мультиарх-сборка из кэша `check` и публикация);
- теги публикации считает шаг `Теги образа`: `:$KIT_VERSION` всегда, `:latest` — только при
  `github.ref == 'refs/heads/main'`;
- `concurrency: docker-agent-${{ github.ref }}` с `cancel-in-progress: true`;
- ограничение платформы: событие, порождённое `GITHUB_TOKEN`, не запускает новых прогонов;
  исключения — `workflow_dispatch` и `repository_dispatch`.

## Goals / Non-Goals

**Goals:**

- Образ с тегом выпущенной версии появляется в реестре по факту релиза, без ожидания расписания.
- Версия kit'а читается из самого образа, а не только из имени тега в реестре.
- Ни одного долгоживущего секрета: работа идёт встроенным токеном рабочего процесса.

**Non-Goals:**

- Синхронная связка «релиз не завершён, пока образ не опубликован». Релиз запускает сборку и
  завершается; ожидание чужого прогона десятками минут (эмуляция arm64) сделало бы релиз заложником
  доступности реестра и раннеров.
- Досборка образов для версий, выпущенных до этого изменения. Разовое выравнивание выполняется
  ручным запуском, механизма для него не заводится.
- Проверка постфактум «для каждого тега `vX.Y.Z` есть образ `:X.Y.Z`». Она сторожила бы то, что
  обеспечивается построением, и противоречила бы требованию `repo-versioning` о согласованности
  носителей построением.

## Decisions

### Запуск сборки образа: `workflow_dispatch` из релизного сценария

Релизный сценарий последним шагом вызывает `gh workflow run docker-agent.yml --ref main` с
`GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`; заданию добавляется право `actions: write`. `gh` предустановлен
на раннере, отдельной установки не требуется.

Шаг ставится **после** `git push origin HEAD` и публикации тега: диспетчеризация по ссылке `main`
поднимает прогон на её текущей вершине, и до появления там релизного коммита прогон прочитал бы
прежний `VERSION` и опубликовал бы прежний тег заново.

Альтернативы:

- **Вызов `docker-agent` как переиспользуемого пайплайна (`workflow_call`) из `release.yml`.** Даёт
  синхронную гарантию и красный релиз при неуспехе сборки, но вызванное задание работает в контексте
  прогона, начавшегося **до** релизного коммита: `actions/checkout` без параметров получил бы
  состояние без нового `VERSION`. Пришлось бы вводить в `docker-agent` входные параметры версии
  и ссылки и поддерживать две схемы получения версии — рассчитываемую и переданную. Цена больше
  выигрыша.
- **Push персональным токеном или ключом развёртывания.** Восстановил бы штатную цепочку
  «push → сборка», но заводит долгоживущий секрет — ровно то, что спецификация `agent-image`
  запрещает для реестра по той же причине: секрет переживает и пайплайн, и потребность в нём.
- **Триггер `push: tags: ['v*']`.** Тег публикуется тем же `GITHUB_TOKEN`, поэтому прогона тоже
  не породит. Не решает проблему.

### Ссылка запуска — `main`, а не тег `vX.Y.Z`

Диспетчеризация принимает и тег, и он указывал бы точно на релизный коммит. Но шаг `Теги образа`
проставляет `:latest` только при `github.ref == 'refs/heads/main'`: запуск по тегу опубликовал бы
`:X.Y.Z` без `latest`, и установленные проекты со значением по умолчанию новую версию не получили бы.
Запуск по `main` даёт оба тега; расхождение вершины `main` с релизным коммитом возможно, только если
между push релиза и стартом прогона в ветку попал ещё один коммит, и `VERSION` он при этом не меняет.

### Метки образа проставляются в обеих сборках, а не только при публикации

`org.opencontainers.image.version` (версия kit'а из `resolve`), `.revision` (`github.sha`) и `.source`
(адрес репозитория) передаются и в сборку задания `check`, и в сборку задания `push`. Иначе проверяется
образ без меток, а публикуется образ с метками — то самое расхождение «проверено одно, опубликовано
другое», ради устранения которого версия OpenSpec уже считается один раз в `resolve`.

Сверка метки добавляется в существующий шаг `Запуск инструментов образа` — там же, где сверяется версия
OpenSpec: метка читается `docker inspect` по загруженному образу и сравнивается с `resolve.kit_version`.
Отдельного задания проверки не заводится: одна лишняя команда в существующем шаге дешевле нового
задания с повторной сборкой.

Метки — стандартные ключи OCI, а не собственные имена: их читают штатные средства реестров и сканеры,
а собственный ключ пришлось бы объяснять в документации.

## Risks / Trade-offs

- **Неуспех сборки после успешного релиза остаётся незамеченным** → шаг диспетчеризации не помечается
  `continue-on-error`, поэтому недоступность API или нехватка прав красят сам релиз; незамеченным
  остаётся только результат уже запущенного прогона. Ограничение зафиксировано в спецификации
  и в `README.md`.
- **Окно, в котором `latest` указывает на предыдущую версию** → сохраняется и равно времени прогона
  `docker-agent` (десятки минут из-за эмулированной сборки arm64). Сокращать его отказом от arm64
  или публикацией до проверки нельзя: обе гарантии дороже окна.
- **`cancel-in-progress` может отменить запущенный релизом прогон** → если сразу после релиза в `main`
  попадает коммит, затрагивающий `Dockerfile`, `VERSION` или сам пайплайн, новый прогон отменит
  предыдущий. Итог не страдает: отменивший прогон читает тот же `VERSION` и публикует те же теги.
  Группу `concurrency` не меняем — иначе очередь заполнялась бы заведомо устаревшими прогонами.
- **Второй носитель версии в образе способен разойтись с тегом** → снимается сверкой метки
  с рассчитанной версией до публикации; при расхождении публикация не выполняется.
- **Право `actions: write` у релизного задания** → позволяет запускать любой пайплайн репозитория.
  Ограничивается тем, что право объявлено у единственного задания сценария, запускаемого вручную
  и только человеком с доступом на запись.

## Migration Plan

1. Изменения вливаются в `main` обычным порядком; сборка образа при этом запускается штатным
   push-триггером — `docker-agent.yml` входит в путевой фильтр — и первой публикует образ с метками.
2. Если тега текущей версии в реестре нет, он проставляется ручным запуском `docker-agent`
   (`workflow_dispatch` по `main`) — тем же механизмом, что и раньше, отдельной оснастки не требуется.
3. Проверка результата: `docker buildx imagetools inspect` показывает тег версии в реестре,
   `docker inspect` загруженного образа — метку версии, совпадающую с `VERSION`.
4. Откат: удаление шага диспетчеризации возвращает прежнее поведение (тег версии появляется
   плановой пересборкой). Откат меток отдельного действия не требует — они не влияют на запуск
   контейнера.

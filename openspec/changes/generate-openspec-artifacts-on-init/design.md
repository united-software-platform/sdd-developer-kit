## Context

Мотивация — в [proposal.md](./proposal.md), требования — в
[specs/kit-installation/spec.md](./specs/kit-installation/spec.md).

Существенные для решения ограничения текущего окружения:

- Цель `make init` выполняется на хосте и до сих пор не требовала ни Docker, ни собранного образа.
- Сервис `claude` объявлен в отдельном compose-профиле `claude`, монтирует рабочее дерево в
  `${PROJECT_DIR:-/app}`, читает `.env` через `env_file` и монтирует каталог профиля аккаунта
  `${CLAUDE_ACCOUNTS_DIR}/${CLAUDE_PROFILE:-__no_profile__}`.
- Версия утилиты закреплена в образе аргументом `OPENSPEC_VERSION` (сейчас `1.11.0`); базовый образ
  запускает процессы от пользователя `claude` с uid/gid 1000.
- Проверено на версии `1.11.0`: `openspec init --tools claude --language ru` неинтерактивен,
  не требует git-репозитория, создаёт `.claude/skills`, `.claude/commands`, `openspec/changes`,
  `openspec/specs` и `openspec/config.yaml`. Повторный запуск обновляет skills и команды, сохраняет
  существующий `openspec/config.yaml` вместе с внесёнными в него правками и не трогает содержимое
  `openspec/changes` и `openspec/specs`. Вывод команды побайтово совпадает с тем, что сейчас лежит
  в репозитории kit'а по этим путям.

Цель `make build` планируется к удалению отдельной задачей, поэтому решение не должно опираться
на её существование в порядке установки.

## Goals / Non-Goals

**Goals:**

- Единственный источник skills, команд агента и конфигурации `openspec/` в целевом проекте — утилита
  из образа, а не архив kit'а.
- Подготовка проекта остаётся одной командой `make init`.
- Инициализацию OpenSpec можно повторить отдельно, не проходя хостовую часть подготовки заново.

**Non-Goals:**

- Порядок шагов установки в `README.md` не перестраивается: правится содержание шага подготовки,
  а не его место.
- Судьба цели `make build` здесь не решается.
- Состав `.claude/` и `openspec/config.yaml` в git-репозитории самого kit'а не меняется.
- Автоматическая доустановка или удаление файлов прежней установки в проектах, где kit уже стоит,
  не выполняется — см. «Migration Plan».

## Decisions

### Отдельная цель `openspec-init`, вызываемая из `init`

Инициализация выносится в самостоятельную цель `make openspec-init`, а `make init` вызывает её
последним шагом, после подготовки `.env`, каталогов, SSH-ключа и конфигурации SSH.

Порядок обязателен: сервис `claude` объявлен с `env_file: .env`, и без созданного `.env` вызов
compose завершится ошибкой. Хостовая часть, выполненная до вызова, остаётся на диске — это и даёт
поведение сценария «Среда контейнеризации недоступна».

Отдельная цель нужна для повторного применения: после обновления `OPENSPEC_VERSION` в образе
инструменты обновляются одной командой, без прохода по хостовой части.

Альтернатива — один монолитный рецепт `init` — отвергнута: инициализацию нельзя было бы вызвать
изолированно, а именно она повторяется чаще остального.

По той же причине цель попадает в белый список host-runner: повторное применение — операция агента,
а не только разработчика. Цель неинтерактивна, поэтому ограничение белого списка на цели, требующие
терминала, её не касается.

### `docker compose run --rm` вместо `exec`

Вызов: `docker compose --profile claude run --rm -T claude openspec init --tools claude --language ru`.

- `run` не требует поднятого контейнера, поэтому подготовка не зависит от `make up` и от очерёдности
  с будущим удалением `make build`; отсутствующий образ compose соберёт на месте.
- `--rm` не оставляет остановленных контейнеров.
- `-T` отключает выделение псевдотерминала: команда неинтерактивна, а без ключа вызов из CI или
  из-под неинтерактивной оболочки может завершиться ошибкой.
- `--tools claude` фиксирует единственный поддерживаемый kit'ом инструмент; `--language ru`
  переносит в вызов ту настройку языка, которая раньше жила в поставляемом `openspec/config.yaml`.

Альтернатива `docker compose exec` отвергнута: она требует уже запущенного контейнера и добавляет
в порядок установки зависимость от `make up`.

Альтернатива «ставить OpenSpec на хост» отвергнута: версия утилиты закреплена в образе, а хостовая
установка вернула бы расхождение версий, ради устранения которого делается change.

### Каталог профиля создаётся до вызова compose

Compose монтирует `${CLAUDE_ACCOUNTS_DIR}/${CLAUDE_PROFILE:-__no_profile__}`. На шаге подготовки
`CLAUDE_PROFILE` обычно ещё не заполнен, а несуществующий каталог bind-монтирования Docker создаёт
сам — от `root`, и удалить его затем обычным пользователем нельзя.

Поэтому цель `openspec-init` создаёт каталог профиля заранее (`mkdir -p`) — заданный в `.env` либо
`__no_profile__`. Каталог `.claude-accounts/` уже вносится в `.gitignore` хостовой частью `init`,
так что в репозиторий заглушка не попадает.

### Из `PAYLOAD_PATHS` уходит и `openspec/config.yaml`

Все три пути — `.claude/skills`, `.claude/commands`, `openspec/config.yaml` — вывод одной и той же
команды. Оставить в поставке один из них означало бы, что в целевом проекте конфигурация приходит
от kit'а, а skills — от утилиты; при расхождении версий это худший вариант, чем оба источника сразу.
После правки в поставке не остаётся ни одного пути `openspec/`.

## Risks / Trade-offs

- **Подготовка проекта начинает требовать Docker.** Раньше `make init` работала на хосте без
  контейнеров → хостовая часть выполняется первой и её результат сохраняется, а сообщение об ошибке
  называет недостающее условие; повторный запуск после старта Docker доводит подготовку до конца.
- **Файлы создаются от uid/gid 1000.** Контейнер пишет `.claude/` и `openspec/` от пользователя
  `claude` → на хосте с другим uid владелец созданных файлов не совпадёт с хозяином рабочего дерева.
  Свойство не новое: агент и так пишет в смонтированное дерево из контейнера, и порядок установки уже
  предполагает совпадение uid.
- **Первый `make init` может занять время сборки образа.** Если образа нет, `docker compose run`
  соберёт его → поведение объясняется в `README.md` на шаге подготовки.
- **Проекты с прежней установкой сохраняют файлы, которые больше не входят в поставку.** Записи
  манифеста по ним исчезают при следующей установке → файлы остаются на диске рабочими, и первый же
  `make init` перезаписывает их выводом актуальной версии утилиты.
- **Смена мажорной версии OpenSpec меняет вывод инициализации.** Расхождение содержания skills между
  проектами, подготовленными в разное время, становится наблюдаемым → это и есть цель change'а:
  версия читается из образа, обновление — повторный `make openspec-init`.

## Migration Plan

Для проекта, где kit уже установлен:

1. Обновить kit штатной командой установки. `.claude/skills`, `.claude/commands`
   и `openspec/config.yaml` в состав поставки больше не входят, поэтому установщик их не трогает
   и подтверждения перезаписи по ним не запрашивает; из нового манифеста записи по ним уходят.
2. Выполнить `make init` (или `make openspec-init`). Инструменты SDD переустанавливаются версией
   утилиты из образа, `openspec/config.yaml` и рабочие артефакты `openspec/changes`, `openspec/specs`
   сохраняются.

Откат: вернуть три пути в `PAYLOAD_PATHS` и убрать вызов `openspec-init` из `init`. Файлы в целевых
проектах при этом уже лежат на своих местах, поэтому откат не требует ручного восстановления.

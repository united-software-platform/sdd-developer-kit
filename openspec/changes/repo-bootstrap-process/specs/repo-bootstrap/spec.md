## Purpose

Описывает наблюдаемый порядок и предусловия сборки рабочего контейнера Claude Code + OpenSpec,
одинаковый для разработчика и CI, до момента готовности контейнера к рабочей сессии агента.

## ADDED Requirements

### Requirement: Предусловия запуска через файл окружения
Сборка и запуск контейнера SHALL требовать наличие файла `.env` с обязательными переменными
окружения. Без файла `.env` или без обязательных переменных запуск контейнера MUST завершаться
ошибкой конфигурации, а не запуском с неполным окружением.

#### Scenario: Запуск без .env
- **WHEN** каталог репозитория не содержит `.env`
- **THEN** запуск контейнера завершается ошибкой конфигурации до начала работы агента

#### Scenario: Запуск с заполненным .env
- **WHEN** `.env` содержит все обязательные переменные окружения
- **THEN** контейнер собирается и запускается без дополнительного вмешательства пользователя

### Requirement: Изоляция профиля аккаунта
Контейнер SHALL видеть только каталог аккаунта, соответствующий заданному профилю (`CLAUDE_PROFILE`).
Контейнер MUST NOT получать доступ на чтение к каталогам других профилей аккаунтов, размещённых
рядом в каталоге всех аккаунтов.

#### Scenario: Профиль не задан
- **WHEN** переменная `CLAUDE_PROFILE` не задана при запуске
- **THEN** контейнер монтирует несуществующий каталог профиля и не получает доступ к каталогам
  существующих профилей

#### Scenario: Профиль задан
- **WHEN** переменная `CLAUDE_PROFILE` указывает на существующий каталог аккаунта
- **THEN** контейнер видит только этот каталог как каталог конфигурации Claude Code

### Requirement: Доступ к git-репозиторию через смонтированные SSH-ключи
Контейнер SHALL получать доступ к SSH-ключам для работы с удалённым git-репозиторием через
смонтированный каталог ключей, а не через ключи, встроенные в образ.

#### Scenario: Push из контейнера
- **WHEN** каталог с приватным и публичным SSH-ключом смонтирован в контейнер и ключ добавлен
  в удалённый git-сервис
- **THEN** команды git внутри контейнера аутентифицируются этим ключом без дополнительной настройки

### Requirement: Единый порядок бутстрапа для разработчика и CI
Последовательность действий по подготовке окружения (сборка образа, запуск контейнера с профилем
аккаунта, готовность к рабочей сессии) SHALL быть одной и той же независимо от того, кто её
выполняет — разработчик вручную или CI-система. Различаться MAY только среда выполнения команд
сборки и запуска, а не сам порядок шагов.

#### Scenario: Бутстрап в CI
- **WHEN** CI выполняет тот же порядок шагов сборки и запуска, что и разработчик вручную
- **THEN** результат — готовый к работе контейнер — не отличается от контейнера, собранного
  разработчиком

### Requirement: Опциональный доступ к целям make без Docker-сокета
Система MAY предоставлять агенту внутри контейнера возможность выполнять ограниченный набор целей
`make` окружения на хосте через отдельный раннер, не выдавая контейнеру доступ к Docker-сокету.
Если этот раннер не запущен на хосте, агент SHALL сохранять возможность работать с исходным кодом
внутри контейнера — отсутствие раннера MUST NOT блокировать бутстрап.

#### Scenario: Раннер не запущен
- **WHEN** host-runner на хосте не запущен
- **THEN** контейнер по-прежнему собирается и запускается, а вызовы целей `make` из контейнера
  завершаются ошибкой соединения, не влияя на остальную работу агента

#### Scenario: Раннер запущен
- **WHEN** host-runner запущен на хосте с заданным токеном
- **THEN** агент внутри контейнера может выполнить разрешённую цель `make` и получить её вывод
  и код возврата

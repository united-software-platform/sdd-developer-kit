## Context

`tools/host-runner/runner.py` выполняет `make {цель} [присваивания…]` в корне репозитория, где
сейчас нет `Makefile`. Белый список (`init`, `up`, `down`, `restart`, `logs`, `authors`, `scan`) и
параметризация (`TARGET_PARAMETERS`, `PARAMETER_PATTERNS`) — наследие проекта, откуда раннер был
перенесён (см. proposal.md — Why). Единственные операции, которые сейчас документированы в
корневом `README.md` и реально нужны агенту без Docker-сокета, — сборка образа и запуск/остановка
контейнера `claude` через `docker compose --profile claude {build|up|down} claude`.

## Goals / Non-Goals

**Goals:**
- Дать репозиторию реальный `Makefile` с целями, которые host-runner может выполнить.
- Сократить поверхность host-runner до этих целей, убрав код, обслуживающий чужие цели и параметры.
- Восстановить `tools/host-runner/README.md` как читаемый документ без дублирования.

**Non-Goals:**
- Не воспроизводится функциональность `authors`/`scan` (снятие слепка стороннего репозитория) —
  она принадлежала другому проекту и её перенос сюда не запрошен.
- Не пересматривается сам протокол host-runner (токен, whitelist, отсутствие shell) — он остаётся
  тем же, меняется только состав целей и наличие параметров.
- Не меняются `docker-compose.yml` и переменные `AGENT_RUNNER_*`.

## Decisions

### Makefile: тонкая обёртка над уже описанными командами `docker compose`
Цели `build`, `up`, `down` вызывают ровно те команды `docker compose --profile claude ...`, что уже
записаны в корневом `README.md` («Сборка образа», «Запуск контейнера»). `up` в `README.md` требует
`CLAUDE_PROFILE` — цель `make up` берёт его из окружения (`docker compose` сам подставит переданную
переменную), а не запрашивает как аргумент `make`: параметризация целей у host-runner убирается
этим изменением, поэтому цель не должна возвращать её через чёрный ход.

Альтернатива — не заводить `Makefile`, а сузить `ALLOWED_TARGETS` до пустого множества (раннер
остаётся установленным, но бесполезным). Отклонена: пользователь явно попросил оставить базовые
`build`/`up`/`down`, а не выключать инструмент.

### Убрать параметризацию целиком, а не оставить неиспользуемый код
`TARGET_PARAMETERS`/`PARAMETER_PATTERNS` существовали только для `authors`/`scan`. Целям `build`,
`up`, `down` параметры не нужны — правило проекта против кода `на будущее` (см. `CLAUDE.md`) не
позволяет оставить эту ветку под гипотетическую цель, которой ещё нет в `Makefile`. `call.sh`
теряет разбор позиционных присваиваний `ПЕРЕМЕННАЯ=значение` и кодирование `args` в base64 —
он снова становится клиентом «цель без параметров».

Если параметризованная цель понадобится в будущем, `TARGET_PARAMETERS`/`PARAMETER_PATTERNS` и
разбор `args` в `call.sh` вводятся заново вместе с этой целью — как было сделано для `authors`/
`scan` версией `1.3.0` (см. версионирование `tools/host-runner/README.md`).

### README переписывается заново, а не патчится построчно
Повреждение (дублирование с обрывом посреди предложения начиная со строки 148) затрагивает и
раздел «Границы доступа» целиком. Патч поверх мусора рискует оставить остатки дублированного
текста; вместо этого документ пересобирается по действующему шаблону `DOC-014` с новым составом
разделов (без `authors`/`scan` и специфичных для них предупреждений о `REPO`/`SNAPSHOT_DIR`).
Версионирование продолжается следующим номером после `1.3.1`, а не сбрасывается — файл не новый.

## Risks / Trade-offs

- [Ветка репозитория, где host-runner уже используется с целями `authors`/`scan`/`restart`/`logs`,
  после этого изменения не сможет их вызвать] → это и есть цель изменения (BREAKING в proposal.md):
  эти цели не выполнимы в текущем `Makefile` репозитория и раньше молча завершались бы ошибкой
  `make: *** No rule to make target`; явный отказ `400` с перечнем разрешённых целей — более
  понятный отказ, чем ошибка `make`.
- [`make up` без заданного `CLAUDE_PROFILE` в окружении, где запущен `runner.py`, ведёт себя как
  `docker compose` без профиля — схлопывает монтирование в несуществующий каталог] → это уже
  задокументированное поведение `docker-compose.yml` (см. `openspec/changes/repo-bootstrap-process`
  — «Изоляция профиля аккаунта»), host-runner его не меняет и не обязан валидировать.

## Migration Plan

Правки вносятся одним изменением без промежуточного состояния: `Makefile` создаётся тем же
изменением, что сокращает `ALLOWED_TARGETS`, — раннер не проходит через стадию, где ссылается на
ещё не созданный `Makefile` с новым списком целей. Отдельного отката, кроме `git revert`, не
требуется: host-runner — опциональный инструмент разработки, не часть рантайма продукта.

## Why

После релиза образ окружения агента с тегом новой версии в реестре не появляется. Релизный сценарий
`release.yml` поднимает `VERSION`, коммитит и пушит в `main` встроенным токеном рабочего процесса,
а push, выполненный `GITHUB_TOKEN`, по устройству GitHub Actions не порождает новых прогонов —
исключение сделано только для `workflow_dispatch` и `repository_dispatch`. Сценарий `docker-agent`,
слушающий push в `main` по пути `VERSION`, релизным коммитом поэтому не запускается: тега `:X.Y.Z`
в реестре нет, а `:latest` остаётся от предыдущей сборки. Путь `VERSION` в фильтре пайплайна
описывает связь, которой фактически нет.

Расхождение затягивает суточная плановая пересборка: она читает уже поднятый `VERSION` и проставляет
недостающий тег — но с задержкой до суток и лишь пока GitHub не отключил расписание за 60 дней
неактивности репозитория. До этого момента закрепление версии образа в `.env` — штатный сценарий
по спецификации `agent-image` — падает с ошибкой «тега нет в реестре» ровно на самой свежей версии
kit'а.

Отдельная сторона той же проблемы: в самом образе версии kit'а нет. Соответствие образа версии
устанавливается только именем тега в реестре, поэтому обнаружить расхождение можно, лишь сверяя
реестр с `VERSION` вручную — что и произошло.

## What Changes

- Релизный сценарий последним шагом явно запускает сборку образа: `workflow_dispatch` сценария
  `docker-agent` на `main` встроенным токеном рабочего процесса. Диспетчеризация — документированное
  исключение из запрета на порождение прогонов токеном, поэтому долгоживущие учётные данные
  не заводятся.
- Запуск выполняется после публикации релизного коммита и тега, поэтому прогон стартует уже на
  релизном коммите, читает поднятый `VERSION` и публикует `:X.Y.Z` и `:latest` — те же теги, что
  и при любой другой публикации из основной ветки.
- Публикация проставляет образу метки OCI: версия kit'а, SHA коммита-исходника и адрес репозитория.
  Версия образа становится проверяемой из самого образа (`docker inspect`), а не только по имени
  тега в реестре.
- Проверка образа сверяет метку версии с версией, рассчитанной заданием параметров, — тем же
  способом, каким уже сверяется версия OpenSpec: расхождение останавливает прогон до публикации.
- Ограничение фиксируется явно: релизный сценарий запускает сборку, но не ждёт её завершения. Отказ
  сборки образа не делает релиз красным, признак — отсутствие тега версии в реестре и красный прогон
  `docker-agent`.
- В `README.md` раздел «Образ окружения агента» дополняется: релиз назван среди событий пересборки,
  описан способ узнать версию образа по метке.

## Capabilities

### New Capabilities

Новых способностей не вводится.

### Modified Capabilities

- `agent-image`: в требование «События пересборки образа» добавляется релиз как событие, порождающее
  публикацию образа с тегом новой версии, и фиксируется, почему push релизного коммита таким событием
  не является. В требование «Схема тегов образа» добавляется носитель версии внутри образа — метки
  OCI; требование «Публикация только после проверки образа» распространяет сверку ожидаемого
  и фактического на версию kit'а в метке.
- `repo-versioning`: требование «Носители версии и их согласованность» дополняется опубликованным
  образом как носителем, согласованность которого с файлом версии обеспечивает релизный сценарий;
  требование «Границы автоматизации git-операций» уточняется — запуск сборки образа входит в один
  запуск релиза и отдельного подтверждения не требует.

## Impact

- Изменяемые файлы: `.github/workflows/release.yml` (шаг запуска сборки образа, право `actions: write`),
  `.github/workflows/docker-agent.yml` (метки OCI при публикации, сверка метки версии в проверке),
  `README.md` (раздел «Образ окружения агента»).
- Состав поставки не затрагивается: оба сценария принадлежат репозиторию kit'а и в целевой проект
  не копируются. `install.sh`, `docker-compose.yml`, `Makefile`, `.env.example` не изменяются.
- Права пайплайна расширяются в одном месте: релизному заданию добавляется `actions: write` —
  без него диспетчеризация сценария невозможна. Права `docker-agent` не меняются.
- Разовое следствие для текущего состояния: тег версии, выпущенной до этого изменения, в реестре
  может отсутствовать. Он проставляется ручным запуском `docker-agent` — отдельного механизма
  досборки прошлых версий не вводится.
- Ограничение, которое изменение не снимает: тег `:latest` между релизом и завершением сборки
  указывает на образ предыдущей версии. Окно — время прогона `docker-agent` (десятки минут из-за
  эмулированной сборки arm64).

## Context

Мотивация — в `proposal.md`, раздел «Why». Здесь только то, что определяет способ.

- Поставка kit'а задана перечнем `PAYLOAD_PATHS` в `install.sh`; файлы ложатся в проект по тем же
  путям, конфликты сверяются с манифестом `.sdd-kit-manifest.json` (`kit-installation`).
- Собственных навыков kit до сих пор не поставлял: `.claude/skills/openspec-*/`
  и `.claude/commands/opsx/` порождает `openspec init`, и `.gitignore` исключает только их.
  Каталог `.claude/skills/project-docs/` версионируется без правки `.gitignore`.
- Прецедент `deliver-make-lint`: правило и средство его исполнения поставляются одной установкой.
- Прецедент `remove-docs-lint`: kit не держит проверок, которые не удерживают действующего
  требования.
- Источник жанра — `README.md`, `CONTRIBUTING.md` и `docs/use-cases.md` проекта formular.
  README kit'а построен иначе (справочник с «Командами» и «Переменными окружения») и нормой
  не покрывается до отдельного выравнивания.

## Goals / Non-Goals

**Goals:**

- Норма, навык и образцы попадают в целевой проект одной установкой и работают без обращения
  к репозиторию kit'а или formular.
- Изменение применимо в любом клоне kit'а: ни одна задача не читает файлов вне его рабочего дерева.
- Навык и образцы не несут второй копии нормы: правка правила `DGN-NNN` доезжает до них без правки.

**Non-Goals:**

- Выравнивание `README.md` kit'а по норме — отдельное изменение по отчёту аудита.
- Аудит и выравнивание документов formular — задачи formular после обновления kit'а.
- Машинная проверка жанра скриптом.
- Норма для прочих документов: правил, глоссария, точек входа `CLAUDE.md` и `AGENTS.md`.
- Поддержка навыка агентами, не читающими `.claude/skills/`: им доступна норма через `AGENTS.md`.

## Decisions

### D1. Отдельный документ правил с префиксом `DGN`, а не продолжение `DOC-*`

`DOC-*` отвечает за формат любого md-файла, `DGN-*` — за роль, каркас и голос трёх конкретных
документов: это разные понятия, и по `TERM-002` им нужны разные имена. Продолжение `DOC-025+`
обязало бы жанром весь набор, включая документы, к которым жанр неприменим.

Отвергнуто: `DOC-025+` — смешение понятий; норма внутри навыка — норма перестала бы быть правилом
набора и не попала бы в `AGENTS.md`.

### D2. Навык поставляется каталогом `.claude/skills/project-docs/` через `PAYLOAD_PATHS`

Один канал установки; путь в проекте совпадает с путём в kit'е. Проверено на `openspec` 1.14.1:
`openspec init --tools claude` сторонний каталог в `.claude/skills/` сохраняет, в том числе
при повторном прогоне, поэтому `make openspec-init` навык не затирает.

Отвергнуто: плагин в маркетплейсе — второй канал установки и вторая версия поставки; навык без
поставки — норма приходила бы без средства её применения, вопреки прецеденту `deliver-make-lint`.

### D3. Образцы — полные документы `shop-cli` в каталоге навыка

Образец и заготовка — один носитель: `templates/readme.md`, `templates/contributing.md`,
`templates/use-cases.md` написаны целиком как документы вымышленного проекта и проходят аудит
без расхождений. Пометки для автора — блок `> **Образец:** …`: HTML-комментарий запрещён `DOC-005`,
а blockquote остаётся штатным Markdown и снимается навыком при порождении.

Лежат образцы в каталоге навыка: `README.md` в корне — файл проекта, и установщик объявил бы
конфликт; в `rules/` образец стал бы документом, который `CLAUDE.md` воспринимает как правило.

Имена образцов отличны от `README.md`, поэтому по `DOC-022` каждый ведёт таблицу версий самого
образца. При порождении `README.md` навык таблицу снимает; для `CONTRIBUTING.md` и документа кейсов
заменяет её начальной записью `1.0.0` проекта.

Отвергнуто: заготовки с пустыми разделами рядом с отдельными образцами — два носителя одного
каркаса, расходящиеся при первой правке; копии документов formular — домен `backlog` нарушает
требование `repo-rules` об общеизвестных предметных областях, ссылки на `plugin/backlog/` в kit'е
ведут в пустоту, снимок расходится с источником, а README formular не несёт обязательных бейджей
и собственной норме не соответствует.

### D4. Норма называет `README.md` и `CONTRIBUTING.md`, путь документа кейсов выбирает проект

Имена двух документов — соглашение платформ размещения репозиториев; путь документа кейсов —
раскладка проекта. Требование `repo-rules` «Структура воплощения правила определяется проектом»
получает об этом оговорку, иначе аудит набора признал бы норму дефектом. Навык находит документ
кейсов по ссылке из «Куда дальше» `README.md`.

### D5. Навык работает в двух режимах: аудит без правок и правка по подтверждению

Аудит выдаёт отчёт: расхождение, код `DGN-NNN`, место. Правка исполняет только подтверждённые
владельцем пункты. Порядок повторяет перенос образца плагина в formular: проверяющий по ходу
проверки ничего не исправляет. Навык называет нормы кодами и путём `rules/project-docs-rules.md`,
своим текстом остаётся только порядок работы и форма отчёта.

### D6. Бейджи: обязательный минимум и запись отсутствующего

Минимум — версия и лицензия: эти бейджи исполнимы в любом проекте, а статус пайплайна зависел бы
от пайплайна, которого kit не поставляет. Изменяемое значение читается из носителя: копия номера
в URL — второй носитель версии. Обязательный бейдж без носителя записывается в «Ограничения»
README; карта «бейдж → источник» ведётся в `CONTRIBUTING.md`, если он есть. Спецификация
`readme-badges` остаётся частным случаем для kit'а: она требует больше минимума и ему не
противоречит.

### D7. Примеры — вымышленный `shop-cli`

`repo-rules` требует общеизвестной предметной области. Инструмент выгрузки каталога товаров
естественно имеет путь пользователя, кейсы, проверки и правящих систему, и при этом не похож
ни на один продукт, из которого норма выведена.

### D8. Отчёт аудита — только по kit'у, в каталоге изменения

`audit/kit.md` обосновывает будущее выравнивание `README.md` kit'а, нормой не является и в поставку
не входит. Аудит formular из изменения исключён: его отчёт нужен formular'у, а задача, читающая
файлы другого репозитория, сделала бы изменение неприменимым вне этого рабочего места. После
обновления kit'а навык стоит в проекте formular, и аудит выполняется там.

### D9. Проверки скриптом нет

По прецеденту `remove-docs-lint`: каркас и голос проверяются чтением, а скрипт с исключениями для
голоса и метки кейса стоил бы сопровождения без удерживаемого требования. Проверкой служит аудит
навыком.

## Risks / Trade-offs

- [Агент без поддержки `.claude/skills/` не получает навык] → норма доступна ему через `AGENTS.md`;
  порядок аудита в навыке короткий и выполним вручную по таблице правил.
- [Проект уже держит свой `.claude/skills/project-docs/`] → установщик показывает конфликт
  и спрашивает подтверждение; случай записывается в «Ограничения» `README.md` kit'а.
- [Будущая версия OpenSpec начнёт очищать `.claude/skills/`] → поведение проверено на 1.14.1
  и записано в D2 с номером версии; автоматической страховки нет, и при смене мажорного разряда
  утилиты проверка повторяется вручную прогоном `make openspec-init` в проекте с навыком.
- [Норма выведена из одного проекта и может оказаться частной] → кейсы и метки оставлены открытым
  перечнем (`DGN` для кейса фиксирует место и форму дополнительных меток, а не их состав);
  CONTRIBUTING допускает разделы проекта между обязательными.
- [Контекст агента растёт на один документ `@`-импорта] → документ держится в объёме прочих правил
  набора; подробности — в навыке и образцах, которые грузятся только по вызову.

## Migration Plan

1. Слияние изменения в `main` kit'а.
2. Релиз `minor` сценарием `release` — запускает человек.
3. Установленные проекты получают норму и навык повторной установкой; новые файлы приходят как
   создаваемые, существующие не меняются.
4. Откат: удаление пути из `PAYLOAD_PATHS` и строк точек входа; в установленных проектах файлы
   остаются и удаляются вручную — установщик файлов не удаляет.

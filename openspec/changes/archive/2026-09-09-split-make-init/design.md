## Context

См. `proposal.md` — Why. Текущее состояние: `Makefile`, цель `init` — один рецепт, где после
`cp .env.example .env` и `mkdir`/`chmod` идёт цикл по `.gitignore`, затем единый shell-блок
`@ssh_key="…"; … ; fi` на ~35 строк с четырьмя `$(call env_value,…)` и вложенными `if`, и в конце
`$(MAKE) --no-print-directory openspec-init` плюс `@echo` с подсказкой. Цель `openspec-init` уже
вынесена отдельно и вызывается из `init`.

Ограничения:

- `help` собирает список целей `grep -E '^[a-zA-Z_-]+:.*?## .*$$'` — цель с описанием `## …`
  и именем из букв, `_` и `-` попадает в вывод автоматически; `init-host` под шаблон подходит.
- `.PHONY` перечисляет цели явно — новую цель нужно туда добавить.
- `env_value` — recursively-expanded переменная `make`, доступна во всех рецептах файла.
- Область правки — только `Makefile` (решение пользователя). `install.sh`, документация,
  белый список host-runner не трогаются; `init` остаётся точкой входа и в белом списке.
- Поведение `make init` фиксируется спецификацией как неизменное: те же файлы, права, сообщения,
  идемпотентность.

## Goals / Non-Goals

**Goals:**

- Вынести хостовую подготовку в одну под-цель `init-host`, идемпотентную и самодостаточную.
- Сохранить `init` как оркестратор: `init: init-host openspec-init` + финальная подсказка.
- Упростить код рецепта: убрать дублирование разрешения переменных `.env`, разбить монолитный
  SSH-блок на именованные шаги, снизить вложенность.
- `make help` показывает `init-host`; описания `init` и `openspec-init` уточнены.

**Non-Goals:**

- Дробление хостовой подготовки на более мелкие цели (`init-env`, `init-ssh-key`, …) — пользователь
  выбрал группировку в 2–3 цели.
- Изменение набора создаваемых файлов, их прав и текстов сообщений.
- Изменение `openspec-init`, `install.sh`, `docker-compose.yml`, белого списка host-runner.
- Переход на `include .env` — запрещено комментарием в `Makefile` (секреты не идут в пространство
  имён `make`).

## Decisions

### Решение 1: Одна под-цель `init-host`, а не набор мелких

`init` разбивается на две зависимости: `init-host` (вся хостовая часть) и существующую
`openspec-init`. Имя `init-host` отражает границу «выполняется на хосте, до контейнера».

Альтернативы:

- Мелкие цели `init-env`/`init-dirs`/`init-gitignore`/`init-ssh` — отклонено: пользователь выбрал
  группировку в 2–3 цели; мелкая нарезка плодит цели, которые по отдельности почти не нужны.
- Оставить всё в `init`, только почистить код — отклонено: не выполняет требование «разбить».

### Решение 2: `init` как список зависимостей, порядок — через зависимости и `.NOTPARALLEL`

`init: init-host openspec-init` с рецептом только из финального `@echo`. Порядок шагов внутри
`init-host` сохраняется рецептом цели; порядок `init-host` → `openspec-init` обеспечивается
последовательностью prerequisites. Для защиты от `make -j` добавляется `.NOTPARALLEL:` (у целей
общий побочный эффект — файлы в корне) либо порядок задаётся явным `$(MAKE)` в рецепте `init`,
как сейчас с `openspec-init`.

Выбор: сохранить текущий приём — рецепт `init` вызывает `$(MAKE) --no-print-directory init-host`
и `$(MAKE) --no-print-directory openspec-init` последовательно. Это ближе всего к нынешнему коду,
не зависит от режима параллельности и не требует `.NOTPARALLEL`.

Альтернатива (prerequisites) отклонена: при `make -j` рецепты пойдут параллельно, а они пишут
в общий `.gitignore`/каталоги.

### Решение 3: Централизовать разрешение переменных `.env`

Ввести одну функцию-обёртку с умолчанием:

```make
# значение из .env или умолчание, если пусто/нет файла
env_or = $(strip $(eval _v := $(call env_value,$(1)))$(if $(_v),$(_v),$(2)))
```

либо оставить `env_value` и один раз в начале рецепта `init-host` присвоить локальные shell-переменные
(`ssh_key=…; ssh_key=$${ssh_key:-.ssh/id_ed25519}`), а дальше по тексту использовать их. Второй
вариант проще и не тянет `eval` в `make`.

Выбор: shell-присвоения в начале одного рецепта `init-host`, сгруппированные блоком; `$(call
env_value,…)` вызывается по одному разу на переменную. Дублирование уходит за счёт того, что весь
SSH-код теперь в одном рецепте с общими переменными, а не размазан.

### Решение 4: Разбить SSH-блок на шаги внутри рецепта

Внутри `init-host` рецепт делится на визуально обособленные секции с комментариями-заголовками:
`.env` → каталоги и права → `.gitignore` → SSH-ключ → SSH-config. SSH-ключ и SSH-config —
два отдельных `@…` блока вместо одного длинного; проверка `ssh-keygen` — отдельный ранний `@…`.
Это снижает вложенность `if` и делает diff при будущих правках локальным.

### Решение 5: Строки `help`

- `init` — «Полная подготовка проекта: хостовая часть и инструменты SDD».
- `init-host` — «Хостовая подготовка: .env, каталоги, SSH-ключ и конфигурация SSH, .gitignore».
- `openspec-init` — описание оставить, при необходимости уточнить «(вызывается из init)».

## Risks / Trade-offs

- [Рефакторинг SSH-блока меняет поведение незаметно] → перед/после сравнить прогон `make init`
  в чистом каталоге и повторный прогон: списки созданных файлов, права (`ls -l .ssh`), тексты
  сообщений должны совпасть побайтово (кроме случайного содержимого ключа).
- [`make -j` ломает параллельные записи в `.gitignore`] → `init` вызывает под-цели через
  последовательные `$(MAKE)`, как сейчас с `openspec-init`; параллелизма между ними нет.
- [Забыть `.PHONY` для `init-host`] → добавить в список; проверить, что цель работает при наличии
  файла/каталога с похожим именем.
- [`init-host` без `openspec-init` оставляет проект без инструментов SDD] → это ожидаемо для
  отдельного вызова; полный путь — `make init`. Отражено в спецификации и в `help`.

## Migration Plan

Единичный коммит с правкой `Makefile`. Откат — обратный коммит. Внешние потребители (`install.sh`,
host-runner, порядок установки в README) не затрагиваются, миграция данных не требуется.
Проверка после правки: `make help` показывает `init-host`; `make init` в свежем временном каталоге
даёт тот же результат, что и до правки; повторный `make init` и одиночный `make init-host`
идемпотентны.

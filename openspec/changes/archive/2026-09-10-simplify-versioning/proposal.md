## Why

Механизм версионирования репозитория состоит из пяти носителей: `VERSION`, `payload.txt`,
`tools/version/check.sh`, `.github/workflows/version-check.yml` и `.github/workflows/release.yml`.
Из них решение принимает человек, а работу выполняет только релизный сценарий — три остальных
существуют ради одной сторожевой проверки «поставка изменена, а `VERSION` не тронут».

Проверка не удерживает то, ради чего заведена: она выполняется на стороне сервиса и сообщает
о пропуске уже после отправки изменений, локальный коммит не блокирует, а её вердикт всё равно
не мешает слить изменения без релиза. Ради неё в репозитории живёт отдельный файл `payload.txt`
и сценарий на 100 строк, читающий git-историю с полной глубиной. Цена сопровождения выше
получаемой гарантии.

## What Changes

**Удаление сторожевого контура**

- Удаляется `.github/workflows/version-check.yml` — пайплайн проверки пропущенной инкрементации.
- Удаляется `tools/version/check.sh` вместе с каталогом `tools/version/`.
- Удаляется `payload.txt`; перечень путей поставки возвращается в `install.sh` как inline-значение
  (переменная `PAYLOAD_PATHS`, как было до введения версионирования). Отдельный файл был нужен
  ради второго читателя — проверки; читателя не стало, и общий файл превратился в лишний носитель.

**Упрощение релиза**

- **BREAKING** Из `release.yml` удаляется входной параметр `task` (код и номер задачи). Единственный
  ввод при запуске — разряд `patch` / `minor` / `major`. Запуски, передававшие два параметра,
  становятся недействительными.
- **BREAKING** Заголовок релизного коммита перестаёт соответствовать формату
  [GIT-009](../../../rules/git-rules.md#формат-сообщения-коммита) `{CODE}-NNN: описание`: без ввода
  задачи взять код и номер неоткуда, а выводить их из контекста запрещает
  [GIT-010](../../../rules/git-rules.md#формат-сообщения-коммита). В `rules/git-rules.md` вносится
  явное исключение для машинного релизного коммита; шаг проверки кода задачи из `release.yml`
  удаляется.
- `VERSION` остаётся единственным источником текущей версии: его читают установщик, бейдж
  `README.md` и релизный сценарий.

**Документация**

- Из `README.md` удаляется описание `payload.txt` и локального прогона `tools/version/check.sh`;
  подраздел «Версия репозитория» переписывается под порядок из двух носителей — `VERSION` и тег.

### Modified Capabilities

- `repo-versioning`: удаляется требование автоматической проверки пропущенной инкрементации вместе
  с требованием общего перечня путей поставки; требование к запуску релиза заменяется на запуск
  с единственным параметром — разрядом — с фиксацией формата сообщения релизного коммита
  и исключения из правил Git; требования о границах автоматизации git-операций и о ненаследовании
  версионирования установленными проектами переформулируются под оставшийся состав механизма.

## Impact

- Удаляемые файлы: `payload.txt`, `tools/version/check.sh` (и каталог `tools/version/`),
  `.github/workflows/version-check.yml`.
- Изменяемые файлы: `install.sh` (возврат `PAYLOAD_PATHS`), `.github/workflows/release.yml`
  (один ввод вместо двух, новое сообщение коммита), `rules/git-rules.md` (исключение для релизного
  коммита), `README.md` (раздел «Версия репозитория»), `VERSION` (инкрементация при релизе).
- Состав поставки не меняется: ни один устанавливаемый в целевой проект файл не затронут.
  Перечень путей поставки остаётся прежним по содержанию — меняется только его носитель.
- Утрачиваемая гарантия фиксируется явно по
  [DOC-020](../../../rules/documentation-rules.md#полнота-содержания): после изменения ничто
  не напоминает о пропущенном релизе — состав поставки может измениться в `main` без повышения
  версии, и обнаружится это только при следующей установке.

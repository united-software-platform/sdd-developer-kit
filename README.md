## Установка

В корне своего проекта:

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh | sh
```

Дальше — по шагам из раздела [Порядок установки](#порядок-установки): подготовка проекта,
заполнение `.env`, запуск контейнера.

Предусловия: Docker с плагином Compose, `make`, `ssh-keygen` (пакет `openssh-client`),
`curl` или `wget`, доступ в интернет.

Если запускать чужой скрипт из сети не хочется, его можно сначала прочитать:

```bash
curl -fsSL -O https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh
less install.sh
sh install.sh
```

Установщик не пишет ничего, пока не покажет план: файлы к созданию, к обновлению и к перезаписи.
Перезапись существующих файлов требует подтверждения.

## Порядок установки

Шаги выполняются в корне вашего проекта по порядку.

**Шаг 1. Установить инструменты**

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh | sh
```

Файлы kit'а появляются в корне проекта. Если какие-то из них там уже есть, установщик покажет
их перечень и спросит подтверждение перед перезаписью.

**Шаг 2. Подготовить проект**

```bash
make init
```

Создаёт `.env` из шаблона, каталоги `.ssh/` и `.claude-accounts/` и дописывает их в `.gitignore`,
чтобы секреты не попали в репозиторий. Затем готовит SSH: генерирует ключ `ed25519` без passphrase
по пути из `SSH_KEY` и печатает публичный ключ. Конфигурацию `.ssh/config` цель создаёт по
заполненному `GIT_HOST` — на этом шаге он ещё пуст, поэтому цель сообщает о повторном запуске.

Цель ничего не перезаписывает: существующие `.env`, ключ и `.ssh/config` остаются как есть,
поэтому её можно запускать повторно.

Последним шагом цель разворачивает инструменты SDD: выполняет `openspec init` в контейнере агента
и создаёт `.claude/skills/`, `.claude/commands/` и каталог `openspec/`. В поставку установщика эти
файлы не входят — их источник утилита OpenSpec той версии, что стоит в образе окружения.
Если образа ещё нет, он загружается из реестра, поэтому первый запуск занимает время загрузки.
Существующие `openspec/config.yaml`, `openspec/changes/` и `openspec/specs/` цель сохраняет,
обновляя только skills и команды агента.

> **Внимание:** шаг требует запущенного Docker и доступа в сеть: образ окружения загружается
> из реестра. Хостовая часть — `.env`, каталоги, SSH-ключ и `.ssh/config` — выполняется до вызова
> контейнера, поэтому при недоступном Docker её результат сохраняется, а цель завершается ошибкой
> на шаге `openspec init`.

**Шаг 3. Заполнить `.env`**

Открыть `.env` и задать значения. Обязательны:

- `GIT_HOST` — хост git-сервиса (например `github.com`);
- `CLAUDE_PROFILE` — имя каталога профиля аккаунта, например `alex`. Переменной нет в шаблоне:
  её значение своё у каждого разработчика.

**Шаг 4. Зарегистрировать ключ и создать профиль**

```bash
make init
mkdir -p .claude-accounts/$(sed -n 's/^CLAUDE_PROFILE=//p' .env)
```

Повторный `make init` создаёт `.ssh/config`: `GIT_HOST` теперь заполнен. Публичный ключ он уже
не печатает — вывод даётся один раз, при создании ключа на шаге 2, поэтому вывести его заново:

```bash
cat .ssh/id_ed25519.pub
```

Этот ключ нужно добавить в git-сервис. Он сгенерирован для проекта и сервису пока неизвестен —
без регистрации push из контейнера не пройдёт.

**Шаг 5. Запустить контейнер**

```bash
make up
```

Собирать ничего не нужно: образ окружения загружается из реестра — подробности в разделе
[Образ окружения агента](#образ-окружения-агента). Перед запуском цель пытается обновить образ
и при недоступном реестре печатает предупреждение, поднимая контейнер на ранее загруженном образе.

**Шаг 6. Войти в контейнер**

```bash
make shell
```

Внутри доступны Claude Code и OpenSpec: `openspec status`, `/opsx:propose` и остальные команды.
Установка окончена.

## Что попадает в проект

Установщик пишет в проект:

| Компонент | Расположение |
|-----------|--------------|
| Окружение агента | `docker-compose.yml`, `Makefile`, `.env.example` |
| Правила репозитория | `rules/`, `CLAUDE.md`, `AGENTS.md` |
| Раннер целей `make` | `tools/host-runner/` |
| Манифест установки | `.sdd-kit-manifest.json` |

Инструменты SDD установщик не переносит — их разворачивает `make init` вызовом `openspec init`
в контейнере агента:

| Компонент | Расположение |
|-----------|--------------|
| Skills и команды агента | `.claude/skills/`, `.claude/commands/` |
| Конфигурация OpenSpec | `openspec/config.yaml`, `openspec/changes/`, `openspec/specs/` |

Так версия этих файлов всегда соответствует версии утилиты в образе, а не той, что лежала в архиве
kit'а на момент установки.

## Образ окружения агента

Контейнер поднимается на готовом образе из GitHub Container Registry (GHCR) — собирать его
в проекте не нужно и нечем: исходник образа в поставку не входит.

| Свойство | Значение |
|----------|----------|
| Имя образа | `ghcr.io/united-software-platform/sdd-developer-kit` |
| Теги | версия kit'а из [`VERSION`](./VERSION) и `latest` |
| Архитектуры | `linux/amd64`, `linux/arm64` в одном мультиарх-образе |
| Состав | базовый образ Claude Code, утилита OpenSpec, интерпретатор Python, менеджер пакетов uv |
| Исходник | [`Dockerfile`](./Dockerfile) в репозитории kit'а |

Собирает и публикует образ сценарий `docker-agent` в GitHub Actions. Публикации всегда предшествует
проверка: образ собирается отдельно под каждую архитектуру, и в нём запускаются все инструменты —
если хоть один не отвечает версией, в реестр не попадает ничего.

Пересборка запускается при правке `Dockerfile` или `VERSION` в основной ветке, раз в сутки по
расписанию и вручную. Суточная пересборка нужна потому, что состав образа зависит от внешних
источников: базовый образ и пакеты инструментов обновляются вне репозитория, и коммитами такие
обновления не сопровождаются. Версия OpenSpec при этом разрешается в пределах закреплённого
мажорного разряда, а версии Python и uv остаются закреплёнными полностью — их смена меняет среду
выполнения проекта и делается правкой `Dockerfile`.

Закрепить версию образа в проекте можно в `.env`, не редактируя файлы поставки:

```bash
SDD_KIT_IMAGE_TAG=1.0.0
```

Тем же способом подставляется собственная сборка — через `SDD_KIT_IMAGE`.

> **Внимание:** тег версии не гарантирует побайтовой неизменности образа. Плановая пересборка
> публикует под тем же тегом обновлённый состав инструментов. Если нужен гарантированно тот же
> самый образ, адресуйте его по digest — он дописывается к тегу:
> `SDD_KIT_IMAGE_TAG=1.0.0@sha256:…`.

> **Внимание:** запуск контейнера в проекте, где образ ещё не загружен, требует сетевого доступа
> к реестру. Раньше сеть была нужна только на шаге установки.

## Команды

| Команда | Действие |
|---------|----------|
| `make init` | Подготовка проекта: `.env`, каталоги, SSH-ключ и `.ssh/config`, записи в `.gitignore`, инструменты SDD |
| `make openspec-init` | Развернуть инструменты SDD: `openspec init` в контейнере агента |
| `make up` | Запуск контейнера агента |
| `make shell` | Вход в контейнер |
| `make down` | Остановка контейнера |
| `make help` | Список команд с описаниями |

Прямые вызовы `docker compose` не нужны ни на одном шаге. В установленном проекте тот же список
всегда доступен по `make help`.

## Переменные окружения

Актуальный состав — в [`.env.example`](./.env.example). Кратко:

| Переменная | Назначение |
|------------|------------|
| `SDD_KIT_IMAGE` | Имя образа окружения агента; по умолчанию — опубликованный образ kit'а |
| `SDD_KIT_IMAGE_TAG` | Тег образа; по умолчанию `latest`, для закрепления версии — номер вида `1.0.0` |
| `PROJECT_DIR` | Путь монтирования рабочего дерева проекта внутри контейнера |
| `CLAUDE_CONFIG_DIR` | Каталог конфигурации Claude Code внутри контейнера |
| `CLAUDE_ACCOUNTS_DIR` | Каталог на хосте, где лежат профили аккаунтов |
| `CLAUDE_PROFILE` | Имя каталога профиля аккаунта; задаётся вручную, в шаблон не входит |
| `CONTAINER_SSH_DIR` | Каталог SSH внутри контейнера |
| `SSH_DIR` | Каталог SSH на хосте, монтируемый в контейнер |
| `SSH_KEY`, `SSH_CONFIG`, `SSH_KNOWN_HOSTS` | Пути к файлам SSH-конфигурации |
| `GIT_HOST`, `GIT_USER` | Параметры доступа к git-хосту |
| `USER_ID`, `GROUP_ID` | UID/GID пользователя контейнера |

> **Важно:** контейнер видит только каталог профиля, заданного `CLAUDE_PROFILE`. Без этой
> переменной монтируется несуществующий каталог — так сделано намеренно, чтобы агент не получил
> доступ к чужим профилям.

## Опционально: host-runner

Внутри контейнера нет ни `make`, ни Docker-сокета, поэтому агент не может сам перезапустить
контейнер или подготовить проект. Если это нужно, на хосте запускается host-runner — узкий канал к
разрешённым целям `make`. Подробности в [`tools/host-runner/README.md`](./tools/host-runner/README.md).

Шаг необязательный: без host-runner всё остальное работает, а вызовы целей `make` из контейнера
просто завершаются ошибкой соединения.

## Повторная установка и обновление

Повторный запуск команды установки обновляет файлы kit'а. Установщик сверяет их с манифестом
`.sdd-kit-manifest.json`:

- файл не менялся с момента установки — обновляется молча;
- файл изменён вами — попадает в перечень перезаписи и требует подтверждения.

Инструменты SDD установщик не обновляет: они не входят в поставку. После обновления kit'а — и после
любого обновления образа окружения, в котором сменилась версия утилиты OpenSpec, — их обновляет
отдельная цель:

```bash
make openspec-init
```

Она переустанавливает skills и команды агента версией утилиты из образа и сохраняет
`openspec/config.yaml` вместе с рабочими артефактами `openspec/changes/` и `openspec/specs/`.

> **Примечание:** в проектах, где kit был установлен раньше, в корне остаётся `Dockerfile` —
> он больше не входит в поставку и ни на что не влияет: `docker-compose.yml` на него не ссылается,
> а установщик файлов не удаляет вовсе. Удалить его можно вручную.

Ключи установщика (при запуске через конвейер передаются как `| sh -s -- КЛЮЧ`):

| Ключ | Действие |
|------|----------|
| `--dry-run` | Показать план и ничего не записывать |
| `--yes` | Не спрашивать подтверждения (для CI) |
| `--ref <REF>` | Установить конкретную ветку, тег или коммит вместо `main` |
| `--source <DIR>` | Взять состав поставки из локального каталога вместо загрузки |

## Ограничения

- **Установка требует сети и публичного репозитория.** Работа в закрытом контуре и установка из
  приватного репозитория не поддерживаются; обходной путь — `--source` с локальной копией kit'а.
- **Слияния файлов нет.** Конфликт разрешается перезаписью целиком: свои цели `Makefile` или разделы
  `CLAUDE.md` нужно перенести вручную после установки.
- **Сбой во время записи оставляет проект частично установленным.** Транзакционного отката нет;
  признак незавершённой установки — отсутствующий или неполный манифест, лечение — повторный запуск.
- **Умолчание `main` невоспроизводимо во времени.** Для повторяемой установки указывайте `--ref`
  с тегом или коммитом.
- **Пути поставки без пробелов.** Список путей и манифест разбираются построчно.

## Разработка самого kit'а

Репозиторий kit'а сам развёрнут теми же инструментами: правила лежат в [`rules/`](./rules),
процесс ведётся через OpenSpec в [`openspec/`](./openspec), установщик — [`install.sh`](./install.sh).
Правила работы с репозиторием описаны в [`CLAUDE.md`](./CLAUDE.md) и [`AGENTS.md`](./AGENTS.md).

Собственные проверки репозитория лежат в [`tools/`](./tools) и запускаются локально до отправки
изменений — тот же вердикт даёт пайплайн:

```bash
sh tools/make-lint/check.sh                 # объём секций Makefile, предел по умолчанию — 30 строк
sh tools/make-lint/check.sh --max-lines 40  # другой предел
```

Секцией считается цель целиком: непрерывный блок комментария перед строкой цели, сама строка цели
и её рецепт. Коды возврата — `0` (пройдено), `1` (есть секции сверх предела), `2` (ошибка вызова
или окружения). Проверки в состав поставки не входят: установленный проект ведёт свой `Makefile`
по собственным правилам.

### Версия репозитория

Версия ведётся по Semantic Versioning 2.0.0 и хранится в двух носителях. Файл [`VERSION`](./VERSION) —
источник истины: он содержит номер без префикса (`1.0.0`), его читает установщик и записывает
в манифест установки, из него же берёт значение бейдж версии. Аннотированный git-тег `vX.Y.Z` —
публикуемая метка того же номера: на него ссылается ключ `--ref` установщика, когда нужна
воспроизводимая установка конкретной ревизии.

Версия повышается, когда изменяется состав поставки — то, что установщик копирует в чужой проект.
Перечень таких путей лежит в [`payload.txt`](./payload.txt); его читают и установщик, и проверка
версии, поэтому второго списка, способного разойтись с первым, в репозитории нет.

Релиз выполняется одним запуском сценария `release` в GitHub Actions — «Run workflow» с двумя
параметрами:

| Параметр | Значение |
|----------|----------|
| `bump` | разряд: `major` — несовместимое изменение состава поставки, `minor` — новая возможность с сохранением совместимости, `patch` — исправление или правка документации |
| `task` | код и номер задачи для заголовка коммита, например `SDDT-012` |

Прогон поднимает `VERSION`, коммитит изменение, ставит аннотированный тег `vX.Y.Z` и публикует его.
Локальной команды инкрементации нет: файл, коммит и тег появляются одним действием, поэтому разойтись
между собой они не могут.

Код задачи задаётся человеком потому, что заголовок коммита обязан соответствовать
[GIT-009](./rules/git-rules.md#формат-сообщения-коммита), а выводить номер задачи из контекста
запрещает [GIT-010](./rules/git-rules.md#формат-сообщения-коммита). Перед записью прогон проверяет,
что в `VERSION` нет незакоммиченных правок — гейт [GIT-020](./rules/git-rules.md#гейт-редактирования).

Пропуск инкрементации замечает проверка — та же, что и в пайплайне:

```bash
sh tools/version/check.sh                 # поставка против HEAD~1
sh tools/version/check.sh --base main     # другая база сравнения
```

Коды возврата — `0` (пройдено), `1` (состав поставки изменён при неизменной версии), `2` (ошибка
вызова или окружения).

Ограничения механизма:

- проверка выполняется на стороне сервиса и обнаруживает пропуск уже после отправки изменений —
  локальный коммит она не блокирует; прогон до отправки остаётся обязанностью автора изменений;
- разряд и задачу выбирает человек: разметка артефактов процесса не различает несовместимые изменения
  внутри изменённого требования, поэтому автоматический вывод разряда занижал бы его именно там, где
  ошибка дороже всего, а номер задачи выводить из контекста запрещено правилами;
- механизм принадлежит этому репозиторию: `VERSION`, `payload.txt`, `tools/version/` и оба сценария
  GitHub Actions в состав поставки не входят и в сценарии OpenSpec не встраиваются — иначе
  в установленном проекте инструкция оказалась бы невыполнимой.

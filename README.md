проекте одной командой.

## Состав набора

Внутри контейнера — инструменты образа окружения агента:

- [claude](https://github.com/united-software-platform/claude) — образ окружения: агент Claude Code
  работает в контейнере, видит только каталог проекта и ходит в git под отдельным аккаунтом
  и SSH-ключом.
- [OpenSpec](https://github.com/Fission-AI/OpenSpec) — ведёт Spec-Driven Development (SDD): его
  командами `/opsx:*` агент создаёт change-артефакты и спецификации в `openspec/`.
- [Python](https://www.python.org) — расширяет возможности агента: на нём агент пишет и запускает
  собственные скрипты и инструменты внутри контейнера.
- [uv](https://github.com/astral-sh/uv) — менеджер зависимостей для Python; им же в образ поставлен
  сам интерпретатор.

В репозитории проекта появляется:

- Окружение агента — `docker-compose.yml`, `Makefile`, `.env.example`: контейнер поднимается
  и обслуживается целями `make`, см. [Команды](#команды).
- [Правила репозитория](./rules) — `rules/`, `CLAUDE.md`, `AGENTS.md`: нормы документации,
  терминологии, чтения, `Makefile` и Git, которые агент читает перед задачей.
- [host-runner](./tools/host-runner) — позволяет агенту запускать команды `make` на вашей машине:
  поднять или перезапустить контейнер. Без него агент видит только исходники; ставится
  [по желанию](#опционально-host-runner).
- Skills и команды SDD — `.claude/skills/`, `.claude/commands/`, `openspec/`: рабочие процессы
  `/opsx:*`, которые разворачивает `make init` вызовом `openspec init`.

Версии инструментов показывают бейджи в начале файла; их значения берутся из
[`Dockerfile`](./Dockerfile) и [`VERSION`](./VERSION) — там их можно прочитать и без бейджей.

Собственные проверки репозитория kit'а в состав набора не входят: в чужой проект они не попадают —
см. [`CONTRIBUTING.md`](./CONTRIBUTING.md#локальные-проверки).

## Установка

В корне своего проекта:

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh | sh
```

Дальше — по шагам из раздела [Порядок установки](#порядок-установки): подготовка проекта,
заполнение `.env`, запуск контейнера.

Предусловия: Docker с плагином Compose, `make`, `ssh-keygen` (пакет `openssh-client`),
`curl` или `wget`, доступ в интернет.

Если запускать чужой скрипт из сети не хочется, его можно сначала прочитать:

```bash
curl -fsSL -O https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh
less install.sh
sh install.sh
```

Установщик не пишет ничего, пока не покажет план: файлы к созданию, к обновлению и к перезаписи.
Перезапись существующих файлов требует подтверждения.

## Порядок установки

Шаги выполняются в корне вашего проекта по порядку.

**Шаг 1. Установить инструменты**

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh | sh
```

Файлы kit'а появляются в корне проекта. Если какие-то из них там уже есть, установщик покажет
их перечень и спросит подтверждение перед перезаписью.

**Шаг 2. Подготовить проект**

```bash
make init
```

Создаёт `.env` из шаблона, каталоги `.ssh/` и `.claude-accounts/` и дописывает их в `.gitignore`,
чтобы секреты не попали в репозиторий. Затем готовит SSH: генерирует ключ `ed25519` без passphrase
по пути из `SSH_KEY` и печатает публичный ключ. Конфигурацию `.ssh/config` цель создаёт по
заполненному `GIT_HOST` — на этом шаге он ещё пуст, поэтому цель сообщает о повторном запуске.

Цель ничего не перезаписывает: существующие `.env`, ключ и `.ssh/config` остаются как есть,
поэтому её можно запускать повторно.

Последним шагом цель разворачивает инструменты SDD: выполняет `openspec init` в контейнере агента
и создаёт `.claude/skills/`, `.claude/commands/` и каталог `openspec/`. В поставку установщика эти
файлы не входят — их источник утилита OpenSpec той версии, что стоит в образе окружения.
Если образа ещё нет, он загружается из реестра, поэтому первый запуск занимает время загрузки.
Существующие `openspec/config.yaml`, `openspec/changes/` и `openspec/specs/` цель сохраняет,
обновляя только skills и команды агента.

> **Внимание:** шаг требует запущенного Docker и доступа в сеть: образ окружения загружается
> из реестра. Хостовая часть — `.env`, каталоги, SSH-ключ и `.ssh/config` — выполняется до вызова
> контейнера, поэтому при недоступном Docker её результат сохраняется, а цель завершается ошибкой
> на шаге `openspec init`.

**Шаг 3. Заполнить `.env`**

Открыть `.env` и задать значения. Обязательны:

- `GIT_HOST` — хост git-сервиса (например `github.com`);
- `CLAUDE_PROFILE` — имя каталога профиля аккаунта, например `alex`. Переменной нет в шаблоне:
  её значение своё у каждого разработчика.

**Шаг 4. Зарегистрировать ключ и создать профиль**

```bash
make init
mkdir -p .claude-accounts/$(sed -n 's/^CLAUDE_PROFILE=//p' .env)
```

Повторный `make init` создаёт `.ssh/config`: `GIT_HOST` теперь заполнен. Публичный ключ он уже
не печатает — вывод даётся один раз, при создании ключа на шаге 2, поэтому вывести его заново:

```bash
cat .ssh/id_ed25519.pub
```

Этот ключ нужно добавить в git-сервис. Он сгенерирован для проекта и сервису пока неизвестен —
без регистрации push из контейнера не пройдёт.

**Шаг 5. Запустить агента**

```bash
CLAUDE_PROFILE=<профиль> docker compose run --rm claude
```

Собирать ничего не нужно: образ окружения загружается из реестра — подробности в разделе
[Образ окружения агента](#образ-окружения-агента). Первый запуск занимает время загрузки образа.

Внутри доступны Claude Code и OpenSpec: `openspec status`, `/opsx:propose` и остальные команды.
Установка окончена — дальше см. [Работа с агентом](#работа-с-агентом).

## Работа с агентом

Рабочая сессия — это контейнер, живущий столько же, сколько сессия: он создаётся на запуске
и удаляется на выходе из агента.

```bash
CLAUDE_PROFILE=<профиль> docker compose run --rm claude
```

Профиль аккаунта берётся из `.env`, а переменная в команде его переопределяет — так на одной машине
работают несколько аккаунтов без правки файлов проекта. Контейнер видит только каталог указанного
профиля: чужие профили ему недоступны.

Если агент при запуске просит авторизацию заново — значит `CLAUDE_PROFILE` указывает на каталог,
которого нет: проверьте имя и наличие каталога в `.claude-accounts/`.

Обновить образ окружения до актуального (плановая пересборка выходит и без смены версии kit'а):

```bash
docker compose pull claude
```

Запуск сессии образ не обновляет сам — без сети он поднимается на уже загруженном образе.

Другие команды в контейнере — оболочка вместо агента, разовый вызов утилиты — и подробности
о работе с образом описаны в репозитории базового образа
[united-software-platform/claude](https://github.com/united-software-platform/claude).

## Что попадает в проект

Что это за компоненты и зачем они нужны — в разделе [Состав набора](#состав-набора); здесь —
куда установщик их пишет.

Установщик пишет в проект:

| Компонент | Расположение |
|-----------|--------------|
| Окружение агента | `docker-compose.yml`, `Makefile`, `.env.example` |
| Правила репозитория | `rules/`, `CLAUDE.md`, `AGENTS.md` |
| Раннер целей `make` | `tools/host-runner/` |
| Манифест установки | `.sdd-kit-manifest.json` |

Инструменты SDD установщик не переносит — их разворачивает `make init` вызовом `openspec init`
в контейнере агента:

| Компонент | Расположение |
|-----------|--------------|
| Skills и команды агента | `.claude/skills/`, `.claude/commands/` |
| Конфигурация OpenSpec | `openspec/config.yaml`, `openspec/changes/`, `openspec/specs/` |

Так версия этих файлов всегда соответствует версии утилиты в образе, а не той, что лежала в архиве
kit'а на момент установки.

## Образ окружения агента

Контейнер поднимается на готовом образе из GitHub Container Registry (GHCR) — собирать его
в проекте не нужно и нечем: исходник образа в поставку не входит.

| Свойство | Значение |
|----------|----------|
| Имя образа | `ghcr.io/united-software-platform/sdd-developer-kit` |
| Теги | версия kit'а из [`VERSION`](./VERSION) и `latest` |
| Архитектуры | `linux/amd64`, `linux/arm64` в одном мультиарх-образе |
| Состав | см. [Состав набора](#состав-набора) |

Закрепить версию образа в проекте можно в `.env`, не редактируя файлы поставки:

```bash
SDD_KIT_IMAGE_TAG=1.0.0
```

Тем же способом подставляется собственная сборка — через `SDD_KIT_IMAGE`.

Из какой версии kit'а собран уже загруженный образ, показывает его метка:

```bash
docker image inspect ghcr.io/united-software-platform/sdd-developer-kit:latest \
    --format '{{index .Config.Labels "org.opencontainers.image.version"}}'
```

> **Внимание:** тег версии не гарантирует побайтовой неизменности образа. Образ пересобирается
> и по расписанию, публикуя под тем же тегом обновлённый состав инструментов. Если нужен
> гарантированно тот же самый образ, адресуйте его по digest — он дописывается к тегу:
> `SDD_KIT_IMAGE_TAG=1.0.0@sha256:…`.

> **Внимание:** первый запуск агента в проекте, где образ ещё не загружен, требует сетевого доступа
> к реестру. Дальше сеть нужна только для обновления образа — см.
> [Работа с агентом](#работа-с-агентом).

Как образ собирается и публикуется — в [`CONTRIBUTING.md`](./CONTRIBUTING.md#образ-окружения-агента).

## Команды

| Команда | Действие |
|---------|----------|
| `make init` | Подготовка проекта: `.env`, каталоги, SSH-ключ и `.ssh/config`, записи в `.gitignore`, инструменты SDD |
| `make openspec-init` | Развернуть инструменты SDD: `openspec init` в контейнере агента |
| `make help` | Список команд с описаниями |

Цели `make` покрывают подготовку проекта; сам агент запускается командой `docker compose` —
см. [Работа с агентом](#работа-с-агентом). В установленном проекте тот же список всегда доступен
по `make help`; у цели `init` есть под-цели по шагам подготовки, их описания там же.

## Переменные окружения

Актуальный состав — в [`.env.example`](./.env.example). Кратко:

| Переменная | Обязательность | Назначение |
|------------|----------------|------------|
| `SDD_KIT_IMAGE` | значение по умолчанию | Имя образа окружения агента; по умолчанию — опубликованный образ kit'а |
| `SDD_KIT_IMAGE_TAG` | значение по умолчанию | Тег образа; по умолчанию `latest`, для закрепления версии — номер вида `1.0.0` |
| `PROJECT_DIR` | значение по умолчанию | Путь монтирования рабочего дерева проекта внутри контейнера |
| `CLAUDE_CONFIG_DIR` | значение по умолчанию | Каталог конфигурации Claude Code внутри контейнера |
| `CLAUDE_ACCOUNTS_DIR` | значение по умолчанию | Каталог на хосте, где лежат профили аккаунтов |
| `CLAUDE_PROFILE` | обязательная; в шаблон не входит | Имя каталога профиля аккаунта — своё у каждого разработчика, поэтому задаётся вручную |
| `CONTAINER_SSH_DIR` | значение по умолчанию | Каталог SSH внутри контейнера |
| `SSH_DIR` | значение по умолчанию | Каталог SSH на хосте, монтируемый в контейнер |
| `SSH_KEY`, `SSH_CONFIG`, `SSH_KNOWN_HOSTS` | значение по умолчанию | Пути к файлам SSH-конфигурации; по `SSH_KEY` цель `make init` создаёт ключ |
| `GIT_HOST` | обязательная | Хост git-сервиса (например `github.com`); по нему `make init` создаёт `.ssh/config` |
| `GIT_USER` | значение по умолчанию | Пользователь git-хоста; по умолчанию `git` |
| `USER_ID`, `GROUP_ID` | значение по умолчанию | UID/GID пользователя контейнера |
| `AGENT_RUNNER_PORT` | по необходимости | Порт host-runner на хосте; нужен, только если раннер используется |
| `AGENT_RUNNER_URL` | по необходимости | Адрес раннера со стороны контейнера — по нему агент вызывает цели `make` |
| `AGENT_RUNNER_TOKEN` | по необходимости | Общий секрет раннера: без совпадающего значения запрос отклоняется. Пустой по умолчанию, задаётся при настройке раннера |

> **Важно:** контейнер видит только каталог профиля, заданного `CLAUDE_PROFILE`. Без этой
> переменной монтируется несуществующий каталог — так сделано намеренно, чтобы агент не получил
> доступ к чужим профилям.

## Опционально: host-runner

Кратко о компоненте — в разделе [Состав набора](#состав-набора); здесь — как он устроен и когда нужен.

Внутри контейнера нет ни `make`, ни Docker-сокета, поэтому агент не может сам подготовить проект
или переустановить инструменты SDD. Если это нужно, на хосте запускается host-runner — узкий канал к
разрешённым целям `make`. Подробности в [`tools/host-runner/README.md`](./tools/host-runner/README.md).

Шаг необязательный: без host-runner всё остальное работает, а вызовы целей `make` из контейнера
просто завершаются ошибкой соединения.

## Повторная установка и обновление

Повторный запуск команды установки обновляет файлы kit'а. Установщик сверяет их с манифестом
`.sdd-kit-manifest.json`:

- файл не менялся с момента установки — обновляется молча;
- файл изменён вами — попадает в перечень перезаписи и требует подтверждения.

Инструменты SDD установщик не обновляет: они не входят в поставку. После обновления kit'а — и после
любого обновления образа окружения, в котором сменилась версия утилиты OpenSpec, — их обновляет
отдельная цель:

```bash
make openspec-init
```

Она переустанавливает skills и команды агента версией утилиты из образа и сохраняет
`openspec/config.yaml` вместе с рабочими артефактами `openspec/changes/` и `openspec/specs/`.

> **Внимание:** после обновления kit'а целей `make up`, `make down` и `make shell` в проекте
> больше нет: рабочая сессия агента открывается командой `docker compose run --rm claude`
> — см. [Работа с агентом](#работа-с-агентом). Скрипты, вызывавшие эти цели, нужно перевести
> на команду запуска сессии.

> **Примечание:** в проектах, где kit был установлен раньше, в корне остаётся `Dockerfile` —
> он больше не входит в поставку и ни на что не влияет: `docker-compose.yml` на него не ссылается,
> а установщик файлов не удаляет вовсе. Удалить его можно вручную.

Ключи установщика (при запуске через конвейер передаются как `| sh -s -- КЛЮЧ`):

| Ключ | Действие |
|------|----------|
| `--dry-run` | Показать план и ничего не записывать |
| `--yes` | Не спрашивать подтверждения (для CI) |
| `--ref <REF>` | Установить конкретную ветку, тег или коммит вместо `main` |
| `--source <DIR>` | Взять состав поставки из локального каталога вместо загрузки |

## Ограничения

- **Установка требует сети и публичного репозитория.** Работа в закрытом контуре и установка из
  приватного репозитория не поддерживаются; обходной путь — `--source` с локальной копией kit'а.
- **Слияния файлов нет.** Конфликт разрешается перезаписью целиком: свои цели `Makefile` или разделы
  `CLAUDE.md` нужно перенести вручную после установки.

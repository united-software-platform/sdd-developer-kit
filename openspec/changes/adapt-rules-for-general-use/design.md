## Context

Мотивация — см. `proposal.md`, раздел «Why». Здесь фиксируется только то состояние, которое
определяет подход.

Четыре адаптируемых документа находятся в `rules/not-adaptated/` в состоянии staged-добавления
(`git status` показывает `A`), то есть их появление в репозитории ещё не зафиксировано коммитом.
Правило [GIT-020](../../../rules/git-rules.md#гейт-редактирования) запрещает вносить новые правки
поверх незакоммиченных: до начала адаптации существующее состояние коммитится отдельно.

Исходные документы неоднородны по стилю примеров: `ddd.md` уже написан псевдокодом
(`Entity Order:`, `Service TransferService:`), а `clean-architecture.md` и `cqrs.md` — исходным
текстом на PHP с `namespace`, `final class`, `readonly`. `docker.md` стоит особняком: его предмет —
сам инструмент, и примеры в нём на YAML и Dockerfile, то есть на формате конфигурации, а не
на языке программирования.

Три документа связаны перекрёстными ссылками: `ddd.md` ссылается на `clean-architecture.md`,
`cqrs.md` опирается на слои из `clean-architecture.md`. Две ссылки ведут наружу набора — на
`php-style.md` и коды `PHP-002`..`PHP-004`, `PHP-008`, которых в репозитории нет.

## Goals / Non-Goals

**Goals:**

- Единый стиль примеров во всех четырёх документах после адаптации.
- Сохранение состава и нумерации норм: код правила остаётся адресуемым извне.
- Замкнутость набора: после правки ни одна ссылка не ведёт на отсутствующий артефакт.
- Предсказуемый порядок работ, в котором репозиторий ни в один момент не содержит правило,
  подключённое в одной точке входа и отсутствующее в другой.

**Non-Goals:**

- Пересмотр самих архитектурных норм. Спор о том, верна ли норма «ссылки между агрегатами только
  по идентификатору», в этой задаче не ведётся — меняется форма записи, не содержание.
- Добавление новых правил в адаптируемые документы.
- Автоматическая проверка технологической нейтральности. Средство контроля набор не получает —
  соответствие проверяется чтением.
- Изменение `install.sh` и состава поставки.

## Decisions

### Решение 1: единый псевдокод в стиле `ddd.md`

Примеры в `clean-architecture.md` и `cqrs.md` переписываются в той же нотации, что уже применена
в `ddd.md`: объявление вида `Entity Order:`, `Service TransferService:`, `Repository OrderRepository:`,
поля с типами через двоеточие, комментарии `// Запрещено` и `// Правильно`.

Обоснование: нотация уже существует в наборе и принята в одном из адаптируемых документов —
брать её дешевле, чем изобретать общий язык примеров. Блоки помечаются как ` ```text `
в соответствии с [DOC-016](../../../rules/documentation-rules.md#код-doc-016), требующим указания
языка.

Альтернативы: оставить примеры на PHP с пометкой «пример на одном из языков» — отвергнуто,
это ровно то, что требуется убрать; перевести примеры на TypeScript или Python как «наиболее
распространённые» — отвергнуто, замена одной привязки на другую.

### Решение 2: коды правил сохраняются, нумерация не пересобирается

`CLAR-001`..`CLAR-023`, `CQRS-001`..`CQRS-006`, `DDD-001`..`DDD-026`, `DOCK-001`..`DOCK-015`
остаются на своих номерах, даже если формулировка правила меняется целиком.

Обоснование: код правила — адрес, на который ссылаются другие документы и сообщения ревью.
Пересборка нумерации обесценила бы все внешние ссылки ради косметики. Тот же принцип уже применён
в наборе — `git-rules.md` сохраняет исторические пропуски в нумерации ровно по этой причине.

### Решение 3: `docker.md` остаётся документом про Docker

Предмет документа — Docker и Compose — сохраняется (решение пользователя). Технологическая
нейтральность достигается не сменой предмета, а снятием привязки к стеку и к проекту:

| Что было привязано | Во что превращается |
|--------------------|---------------------|
| Префикс из `README` системы «RAG-система Lenvendo», сервисы `rag-*` | Префикс проекта как норма; источник префикса — имя проекта; примеры на нейтральных именах |
| Диапазон портов `11000–12000` | Обязанность проекта задать свой диапазон и не публиковать порты по умолчанию |
| Пользователь и группа `www`, `Dockerfile` на `php:8.4-fpm` | Непривилегированный пользователь приложения; `Dockerfile` в примере — без привязки к языку |
| «Backend-контейнер» как класс сервиса | Контейнер приложения |

Правила `DOCK-003`..`DOCK-007`, `DOCK-009`..`DOCK-011`, `DOCK-014`, `DOCK-015` содержательно
нейтральны уже сейчас: правятся только имена в примерах.

Альтернатива — обобщить документ до «правил оркестрации контейнеров» без упоминания Compose —
отвергнута пользователем: норма вроде «`env_file` запрещён» без имени инструмента становится
непроверяемой.

### Решение 4: структура каталогов заменяется логическими слоями

Деревья `src/{Module}/Domain/...` из `clean-architecture.md` и `cqrs.md` удаляются. Слой описывается
как логическая группа с явной оговоркой о свободе физического воплощения. Затронутые правила:

- `CLAR-011` («каждый UseCase живёт в собственном каталоге») → каждый сценарий использования
  образует собственную единицу группировки вместе со своими входным и выходным контрактами;
- `CLAR-022`, `CLAR-023` (module-first) — норма сохраняется: группировка по доменным модулям,
  а не по техническим слоям. Меняется только иллюстрация: вместо дерева каталогов — схема
  вложенности слоёв в модуль;
- `CQRS-001`, `CQRS-003` — принадлежность интерфейса слою (домен против приложения) остаётся
  нормой, путь к файлу уходит.

Схема слоёв в `clean-architecture.md`, нарисованная псевдографикой, сохраняется: она изображает
направление зависимостей, а не раскладку файлов.

### Решение 5: `CLAR-005` удаляется, `DDD-024` переформулируется самодостаточно

Обе ссылки ведут на `php-style.md`, которого в наборе нет и содержимое которого недоступно.
Восстановить исходный текст `PHP-002`..`PHP-004`, `PHP-008` невозможно.

- `CLAR-005` («Domain: → см. PHP-002, PHP-003, PHP-004») **удаляется целиком** — решение
  пользователя при выполнении задачи 1.2. Правило состояло из одной отсылки: без исходного документа
  у него нет собственного содержания, а восстановление «по смыслу» ввело бы в свод норму, которой
  никто не формулировал. Номер `CLAR-005` остаётся незанятым: нумерация прочих правил сохраняется
  (решение 2), в документе появляется пропуск с примечанием о неизменности кодов — тот же приём,
  что уже применён в `git-rules.md`.
- `DDD-024` теряет хвост «(см. `php-style.md`, PHP-004, PHP-008)»; сама норма — объект не создаёт
  сам себя, создание идёт через фабрику или конструктор с внешними аргументами — уже записана
  в правиле полностью и в ссылке не нуждается.

Альтернатива — восстановить `CLAR-005` по смыслу соседних норм (запрет глобального состояния,
статических точек доступа и самосоздания объектов в домене) — рассмотрена и отклонена пользователем:
правило, выведенное из догадки о содержании недоступного документа, выдаёт допущение за норму.

> **Внимание:** запрет глобального состояния в домене после удаления `CLAR-005` прямой нормой свода
> не является. Частично он покрывается `DDD-019` (Domain Service не хранит состояние) и `DDD-024`
> (объект не создаёт сам себя). Если норма нужна целиком, её следует ввести отдельной задачей
> и сформулировать заново, а не восстанавливать из отсылки.

### Решение 6: обнуление версий — одна запись `1.0.0`

Таблица версий каждого документа сводится к единственной строке: версия `1.0.0`, дата выполнения
задачи, задача — эта OpenSpec change, агент и модель — по [DOC-022](../../../rules/documentation-rules.md#жизненный-цикл-документа).
Прежние записи (`1.0.1`, `1.0.2`, `1.1`, `1.2`) не переносятся.

Обоснование: перенесённая история описывает изменения документа в другом проекте и в контексте
набора нечитаема — она ссылается на задачи и правила, которых здесь нет. Дата принятия
и ссылка на задачу адаптации — единственная история, имеющая для набора смысл. Сама история
переноса при этом не теряется: она остаётся в системе контроля версий.

### Решение 7: порядок работ — содержимое, затем перенос, затем подключение

1. Коммит незафиксированного состояния `rules/not-adaptated/` ([GIT-020](../../../rules/git-rules.md#гейт-редактирования)).
2. Адаптация содержимого каждого документа на месте.
3. Перенос четырёх файлов в `rules/`, удаление каталога `not-adaptated/`.
4. Подключение в `CLAUDE.md` и `AGENTS.md` — одной правкой оба файла.

Обоснование порядка: подключение последним шагом гарантирует, что в контекст агента ни в один
момент не попадает документ в неадаптированном виде. Перенос отдельным шагом от правки содержимого
делает изменение читаемым в diff: перемещение файла не смешивается с переписыванием его текста.

## Risks / Trade-offs

- **Рост контекста агента.** Четыре документа (~60 КБ) переходят в `@`-импорты `CLAUDE.md`
  и загружаются при каждом запуске. → Размен принят осознанно: правила архитектуры влияют
  на каждую задачу написания кода, и правило, о котором агент не знает, не действует. Если рост
  окажется ощутимым, отдельной задачей часть документов переводится в подключение по ссылке
  без `@`-импорта.
- **Потеря буквы правила при переформулировке `CLAR-005`.** → Допущение зафиксировано явно
  в решении 5 и выносится пользователю при сдаче работы.
- **Псевдокод допускает разночтения.** Норма, записанная без синтаксиса языка, может быть понята
  двояко — например, «неизменяемость» в языке без `readonly`. → Каждая такая норма
  сопровождается формулировкой через наблюдаемое свойство («изменение создаёт новый объект»),
  а не через механизм языка.
- **Правила становятся общими и теряют остроту.** Убрав стек, легко скатиться к формулировкам,
  которые ничего не запрещают. → Критерий приёмки: каждое правило после адаптации сохраняет
  проверяемость — по нему можно указать на конкретный фрагмент кода и сказать, нарушает он норму
  или нет. Правило, потерявшее это свойство, переформулируется, а не оставляется общим.
- **Документы уходят в поставку сразу.** `install.sh` включает `rules/` целиком, отдельного
  переключателя состава нет. → Это же и цель изменения; отката на «поставлять не всё» не требуется.

## Migration Plan

Отдельной миграции не требуется: изменение затрагивает только документы репозитория. Установленные
ранее проекты получают адаптированные правила при следующей установке kit'а — манифест установки
перечисляет файлы, и исчезнувший `rules/not-adaptated/` перестаёт попадать в поставку.

Откат — возврат коммита: содержимое документов восстанавливается целиком, поскольку изменение
не затрагивает ни кода, ни состояния.

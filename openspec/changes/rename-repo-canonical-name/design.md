## Context

См. `proposal.md` — Why. Переименование репозитория на GitHub — внешнее действие над общим
ресурсом (меняет URL, видимый всем, кто уже склонировал репозиторий или ссылается на него).

## Goals / Non-Goals

**Goals:**
- Зафиксировать порядок переименования репозитория и синхронизации локального `git remote`.
- Явно решить, кто выполняет переименование на GitHub — пользователь или агент.

**Non-Goals:**
- Не переименовывается организация `united-software-platform` и Docker-образы (`claude-openspec`,
  `ghcr.io/united-software-platform/claude`) — они не входят в замеченное расхождение.
- Не правятся исторические записи версионирования (`ReqControl`, `experience-graph`) в
  `tools/host-runner/README.md` — это история изменений, актуальность имени она не отражает.

## Decisions

**Переименование на GitHub выполняет пользователь, а не агент.** Переименование репозитория —
действие над внешним аккаунтом/организацией, видимое всем участникам и меняющее URL для всех, у
кого уже есть клон. Это тот же класс риска, что и добавление SSH-ключа в аккаунт ранее в этой
сессии — явное подтверждение пользователя обязательно перед выполнением, а не после.
Технически возможно через `gh repo rename sdd-developer-kit --repo united-software-platform/ssd-developer-kit`,
но запуск инициирует пользователь.

**После переименования на GitHub агент обновляет `git remote` в этой рабочей среде.**
`git remote set-url origin` — локальная, обратимая операция, безопасная для выполнения агентом
сразу после подтверждения, что переименование на GitHub прошло.

## Risks / Trade-offs

- [Риск] Старый URL `ssd-developer-kit` может быть где-то захардкожен вне этого репозитория (CI
  других проектов, документация, закладки). → Смягчение: GitHub сохраняет редирект со старого имени
  на новое, поэтому `git clone`/`git fetch` по старому URL продолжают работать после переименования.
- [Риск] Одновременное переименование и незакоммиченные изменения в этой рабочей среде могут
  создать путаницу с тем, какой remote актуален. → Смягчение: `git remote set-url` выполняется отдельным
  шагом сразу после подтверждения переименования, до дальнейших `git push`.

## Migration Plan

1. Пользователь переименовывает репозиторий на GitHub (`ssd-developer-kit` → `sdd-developer-kit`).
2. Агент обновляет `git remote set-url origin` в этой рабочей среде на новый URL.
3. Агент проверяет `git push`/`git fetch` с новым URL.
4. Правки `README.md` (заголовок, упоминания) коммитятся отдельно от смены remote — это
   независимые шаги, откат одного не требует отката другого.

Откат: переименование на GitHub обратимо тем же способом в обратную сторону; `git remote set-url`
откатывается на старый URL без потери истории.

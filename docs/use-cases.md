## Кейс 1. Хочу прочитать установщик до запуска

**Когда.** Я не хочу запускать чужой скрипт из сети по конвейеру, пока не увижу, что он делает.

**Что делаю.** Скачиваю установщик, читаю его, смотрю план и только потом запускаю:

```bash
curl -fsSL -O https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh
less install.sh
sh install.sh --dry-run
sh install.sh
```

**Что получаю.** Тот же состав, что и при установке по конвейеру. Ключ `--dry-run` показывает
файлы к созданию, к обновлению и к перезаписи и ничего не записывает.

## Кейс 2. Хочу установить конкретную ревизию набора или поставить его без сети

**Когда.** Мне нужна повторяемая установка, а ветка `main` по умолчанию со временем меняется. Или
машина не может скачать набор: закрытый контур, приватная копия репозитория.

**Что делаю.** Для повторяемой установки называю тег или коммит ключом `--ref`. При запуске через
конвейер ключи передаются после `sh -s --`:

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/sdd-developer-kit/main/install.sh | sh -s -- --ref vX.Y.Z
```

Без загрузки — переношу на машину копию репозитория набора и указываю её ключом `--source`:

```bash
sh <копия набора>/install.sh --source <копия набора>
```

**Что получаю.** В проекте файлы выбранной ревизии или локальной копии. Образ окружения при этом
всё равно загружается из реестра на шаге подготовки проекта: без доступа к реестру подготовка
останавливается на `openspec init`.

## Кейс 3. Хочу работать в проекте под несколькими аккаунтами

**Когда.** На одной машине я работаю под разными аккаунтами Claude Code, а в `.env` записан один
профиль.

**Что делаю.** Завожу каталог второго профиля и называю профиль в команде запуска — переменная
в команде переопределяет значение из `.env`:

```bash
mkdir -p .claude-accounts/<второй профиль>
CLAUDE_PROFILE=<второй профиль> docker compose run --rm claude
```

**Что получаю.** Сессию агента под вторым аккаунтом без правки файлов проекта. Контейнер видит только
каталог указанного профиля — чужие профили ему недоступны.

## Кейс 4. Хочу обновить образ окружения

**Когда.** В реестре вышел свежий образ — новый выпуск Claude Code или OpenSpec, а сессия поднимается
на загруженном раньше: запуск сессии образ сам не обновляет. Свежий образ выходит и без смены версии
набора.

**Что делаю.** Загружаю образ:

```bash
docker compose pull claude
```

Если в новом образе сменилась версия OpenSpec — её показывает бейдж в начале
[`README.md`](../README.md), — переустанавливаю skills и команды OpenSpec:

```bash
make openspec-init
```

**Что получаю.** Следующая сессия идёт на свежем образе, skills и команды OpenSpec соответствуют
утилите в нём. `openspec/config.yaml`, `openspec/changes/` и `openspec/specs/` остаются как были.
Без сети сессия поднимается на уже загруженном образе. Если образ закреплён по кейсу 5, команда
загружает закреплённый образ.

## Кейс 5. Хочу закрепить образ окружения

**Когда.** Мне нужно, чтобы в проекте работал один и тот же состав, или свежий выпуск оказался
неработоспособным и я возвращаюсь к прежнему.

**Что делаю.** Образ — `ghcr.io/united-software-platform/sdd-developer-kit` в GitHub Container
Registry (GHCR), мультиарх: `linux/amd64` и `linux/arm64`. Выбираю тег:

- `latest` — свежий проверенный состав, значение по умолчанию;
- **версия набора** (`X.Y.Z`) — свежий состав, собранный на этой версии набора. Тег подвижный:
  каждая пересборка переставляет его на новый образ;
- **тег состава** (`X.Y.Z-YYYYMMDD-hhmmss`, время публикации в UTC) — конкретная публикация. Тег
  не перезаписывается, по нему я возвращаюсь к составу, работавшему раньше.

Записываю выбор в `.env`, не трогая файлы поставки:

```bash
SDD_KIT_IMAGE_TAG=X.Y.Z                 # версия набора, состав — свежий
SDD_KIT_IMAGE_TAG=X.Y.Z-YYYYMMDD-hhmmss # конкретная публикация
SDD_KIT_IMAGE_DIGEST=@sha256:…          # тот же самый образ побайтово
```

Что внутри загруженного образа, смотрю по его меткам, не запуская контейнер:

```bash
docker image inspect ghcr.io/united-software-platform/sdd-developer-kit:latest \
    --format '{{json .Config.Labels}}'
```

Выпуск Claude Code — в `org.opencontainers.image.base.name`, выпуск OpenSpec —
в `io.sdd-kit.openspec.version`, версия набора — в `org.opencontainers.image.version`.

**Что получаю.** Сессии поднимаются на выбранном образе.

> **Внимание:** тег версии набора не гарантирует побайтовую неизменность образа: он адресует версию
> исходников, а не состав. Гарантию даёт только `SDD_KIT_IMAGE_DIGEST`; заданный digest определяет
> образ независимо от тега.

## Кейс 6. Хочу запустить агента на своей сборке образа

**Когда.** Я собрал собственный образ окружения и хочу работать в нём, а не в опубликованном.

**Что делаю.** Называю свой образ в `.env` и запускаю сессию как обычно:

```bash
SDD_KIT_IMAGE=<имя моего образа>
SDD_KIT_IMAGE_TAG=<тег моего образа>
```

**Что получаю.** Сессию агента в моём образе без правки файлов поставки.

## Кейс 7. Хочу, чтобы агент сам запускал цели make

**Когда.** Агенту нужно подготовить проект или переустановить инструменты SDD, а в контейнере нет
ни `make`, ни Docker-сокета: вызовы целей `make` из контейнера завершаются ошибкой соединения.

**Что делаю.** Запускаю на хосте host-runner — узкий канал к разрешённым целям `make` — по
[`tools/host-runner/README.md`](../tools/host-runner/README.md). В `.env` для него нужны:

- `AGENT_RUNNER_TOKEN` — общий секрет раннера: без совпадающего значения запрос отклоняется;
  по умолчанию пуст, задаю его сам;
- `AGENT_RUNNER_PORT` — порт раннера на хосте;
- `AGENT_RUNNER_URL` — адрес раннера со стороны контейнера, по нему агент вызывает цели.

**Что получаю.** Агент вызывает разрешённые цели `make` и получает их вывод и код возврата. Без
раннера всё остальное работает как прежде.

## Кейс 8. Хочу обновить набор в проекте

**Когда.** Вышла новая версия набора, а в проекте стоит прежняя.

**Что делаю.** Повторяю команду установки из шага 1 [`README.md`](../README.md). Установщик сверяет
файлы с манифестом `.sdd-kit-manifest.json`:

- файл не менялся с момента установки — обновляется молча;
- файл изменён мной — попадает в перечень перезаписи и требует подтверждения.

Инструменты SDD установщик не обновляет, поэтому затем переустанавливаю их:

```bash
make openspec-init
```

**Что получаю.** Файлы набора новой версии; `openspec/config.yaml`, `openspec/changes/`
и `openspec/specs/` остаются как были.

> **Внимание:** после обновления целей `make up`, `make down` и `make shell` в проекте больше нет:
> сессия агента открывается командой `docker compose run --rm claude`. Скрипты, вызывавшие эти цели,
> я перевожу на эту команду.

> **Примечание:** если набор стоял в проекте давно, в корне остаётся `Dockerfile`. Он больше
> не входит в поставку и ни на что не влияет: `docker-compose.yml` на него не ссылается, а установщик
> файлов не удаляет. Удаляю его вручную.
